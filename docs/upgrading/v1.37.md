# Upgrading to Lockspire v1.37

v1.37 keeps the v1.x resource-server and client-registration surface additive.
It does not remove the `%Lockspire.AccessToken{}` struct or change the meaning
of its raw claims. This guide helps existing Phoenix hosts adopt the new
preferred readers and the durable DPoP replay default without a semantic
migration of existing code.

## Prefer semantic access-token readers

After `Lockspire.Plug.VerifyToken` succeeds, the verified token remains in
`conn.assigns.access_token`. The existing raw `claims` map remains available
for compatibility and extension data. New code should prefer the additive
readers:

```elixir
access_token = conn.assigns.access_token

subject = Lockspire.AccessToken.subject(access_token)
scopes = Lockspire.AccessToken.scopes(access_token)
audiences = Lockspire.AccessToken.audiences(access_token)
expires_at = Lockspire.AccessToken.expires_at(access_token)
confirmation = Lockspire.AccessToken.confirmation(access_token)
```

The supported calls are `Lockspire.AccessToken.subject/1`,
`Lockspire.AccessToken.scopes/1`, `Lockspire.AccessToken.audiences/1`,
`Lockspire.AccessToken.expires_at/1`, and
`Lockspire.AccessToken.confirmation/1`. They return normalized protocol facts:
subject is a nonblank string or `nil`; scopes and audiences are normalized lists;
expiration is a `DateTime` or `nil`; and confirmation is an allowlisted sender
binding map or `nil`. The raw `claims` map remains available, so existing hosts
that intentionally consume an extension claim do not need to rewrite it.

Lockspire still validates protocol, route scope, audience, and sender
constraints. Your host continues to authorize tenants, objects, billing,
product responses, and its own rate limits after those protocol checks.

## DPoP replay storage default

The canonical `Lockspire.Plug.EnforceSenderConstraints` configuration now uses
the configured Lockspire repository as its durable DPoP replay store by default.
Remove a redundant `dpop_replay_store:` option if it existed only to make the
ordinary installed pipeline work.

The custom replay stores remain supported for applications that deliberately own a
compatible durable implementation:

```elixir
plug Lockspire.Plug.EnforceSenderConstraints,
  dpop_replay_store: MyApp.DpopReplayStore
```

This is an advanced override. A missing, incompatible, or failing custom store
rejects the DPoP proof; Lockspire does not silently fall back to accepting it.

## Registration capability clarification

Direct registration and dynamic client registration now share the same narrow
shape rules. `openid` is a built-in OIDC scope. A device-code-only client may
omit redirect URIs only when it has neither `authorization_code` nor a `code`
response type. Any authorization-code or `code` response shape still requires
non-empty redirect URIs and the existing exact-match redirect validation at the
authorization boundary.

`private_key_jwt` remains limited to confidential clients on the existing
Lockspire-owned direct-client endpoints. It requires exactly one validated key
source: inline `jwks` or HTTPS `jwks_uri`. This clarifies existing supported
constraints; it does not add a generic JWT client-auth mechanism, a hosted
service, or a formal certification claim.

## No required deprecation action

No callable public API is deprecated by this release. The readers are additive,
and raw claims remain the compatibility path for extensions. See
[Protect Phoenix API Routes](../protect-phoenix-api-routes.md) for the canonical
generated-route and host-authorization contract.
