# Phase 116 - UI Design Contract

> Visual and interaction contract for Phase 116: Inventory, Rubric & Lab Contract. Generated by gsd-ui-researcher, pending verification by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Phoenix LiveView function components plus embedded Lockspire admin CSS |
| Preset | Not applicable; no shadcn, Tailwind, React Storybook, PhoenixStorybook, or third-party registry in this phase |
| Component library | `Lockspire.Web.Components.AdminComponents` with Phoenix `attr/3` and `slot/3` contracts |
| Icon library | None required for Phase 116 inventory contracts; do not introduce an icon dependency |
| Font | `--ls-font-display` Familjen Grotesk stack for headings, `--ls-font-sans` Inter stack for UI/body, `--ls-font-mono` JetBrains Mono stack for identifiers |

**Source of truth:** `brandbook/`, `brandbook/tokens/tokens.json`, `lib/lockspire/web/admin_css.ex`, `lib/lockspire/web/components/admin_components.ex`, and `lib/lockspire/web/admin_router.ex`.

**Stack contract:** Phase 116 targets Phoenix `1.8.5` and Phoenix LiveView `1.1.28` admin surfaces. Implementation planning must preserve the embedded-library shape: hosts own operator authentication, layouts, tenant policy, and outer branding before mounting `Lockspire.Web.AdminRouter`; Lockspire owns protocol/admin state after the request reaches the mounted LiveViews.

**Lab/tooling contract:** The component lab is maintainer/demo/test-only. It may be an ExUnit-rendered stress surface or repo-local demo proof, but it must not mount through `Lockspire.Web.AdminRouter`, create a new supported admin route, publish a public API, add PhoenixStorybook, add a React/JS Storybook shell, create public theming, or create a host-editable component registry.

## Spacing Scale

Declared values use the existing `--ls-space-*` tokens and remain multiples of 4px:

| Token | Value | Usage |
|-------|-------|-------|
| xs / `--ls-space-1` | 4px | Icon gaps, inline badge gaps, fine focus/label spacing |
| sm / `--ls-space-2` | 8px | Compact element spacing, button vertical padding, badge padding |
| md / `--ls-space-4` | 16px | Default element spacing, card padding, field grouping |
| lg / `--ls-space-6` | 24px | Section padding, page group spacing, major form grouping |
| xl / `--ls-space-8` | 32px | Layout gaps, shell/header spacing, major admin groups |
| 2xl / `--ls-space-12` | 48px | Page-level breaks and route group separation |
| 3xl | 64px | Reserved page-level spacing only; do not add unless a later implementation phase proves the need |

Exceptions:

- `--ls-space-3` is allowed for existing 12px compact rows, labels, and mobile-sensitive resource rows.
- `--ls-space-5` is allowed for existing 20px card/body rhythm.
- `--ls-space-10` is allowed for existing 40px shell or control-related gaps.
- `--ls-control-height` remains 40px for form controls and buttons. Touch target exceptions must preserve at least 40px height in the admin UI; do not add smaller click targets.
- Phase 116 may document spacing gaps in inventories, but it must not change CSS.

## Typography

Use exactly these four sizes and two weights in the contract:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px / `--ls-type-label-size` | 600 for labels and badge text | 1.2 |
| Body | 14px / `--ls-type-body-size` | 400 | 1.5 |
| Heading | 16px / `--ls-type-heading-size` | 600 | 1.25 |
| Display | 24px / `--ls-type-display-size` | 600 | 1.2 |

Rules:

- Body text uses the Inter stack via `--ls-font-sans`.
- Headings use the Familjen Grotesk display stack where existing admin CSS applies it.
- Identifiers, token handles, URLs, JWK/thumbprint-like values, and long protocol strings use the JetBrains Mono stack via `--ls-font-mono`.
- Do not add new font files or external font fetches.
- Do not introduce viewport-scaled type. Long identifiers must wrap through layout and `long_value` patterns, not font shrinking.

## Color

Use brandbook semantic tokens as the canonical color contract. Dark mode remaps semantic aliases only; primitive colors remain stable.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Light: `--ls-surface-page` `#f8fafc`; Dark: `--ls-surface-page` `#0b1220` | Page background, admin shell body, broad route surfaces |
| Secondary (30%) | Light: `--ls-surface-panel` `#ffffff`; Dark: `--ls-surface-panel` `#131c2e` | Cards, section panels, resource rows, nav/shell panels |
| Accent (10%) | Light text/action: Deep Cyan `#0e7490`; Dark/hero/focus/non-text: Signal Cyan `#22d3ee` | Focus rings, primary actions, active navigation, key status emphasis, hero/brand accents |
| Destructive | Light: `--ls-status-danger-*` with text `#991b1b`; Dark: `--ls-status-danger-*` with text `#fca5a5` | Destructive actions, destructive confirmations, danger badges and alerts only |

Accent reserved for:

- Primary CTAs in admin workflows.
- Focus ring and focus glow.
- Active navigation/selected route states.
- Non-text brand/focus accents on dark surfaces.
- Status/info emphasis where semantic `info` tokens apply.

Accent is not reserved for all links, all badges, all borders, or generic decoration. Signal Cyan `#22d3ee` must not be used as normal light-mode text or small light-mode UI; use Deep Cyan `#0e7490` or `#155e75` for light-mode text/actions.

Status color rules:

- Every status badge must carry a visible text label; color alone is insufficient.
- Phase 116 inventory must expose all real Configure, Support, and Operate status atoms that currently fall through to generic/disabled styling.
- Destructive and warning states must use semantic status tokens, not raw hex outside token declarations.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Record inventory contract` |
| Empty state heading | `No inventory gaps recorded` |
| Empty state body | `Derive the route list from AdminRouter, append the logout-propagation workflow, then record missing component states before implementation starts.` |
| Error state | `Inventory proof drifted from source. Re-read AdminRouter, AdminComponents, and brandbook tokens, then update the contract before planning implementation.` |
| Destructive confirmation | `No new destructive runtime action in Phase 116. If the inventory finds a destructive action, record its existing confirmation copy and consequence; do not add retry, discard, logout, revoke, rotate, or delete behavior unless an existing domain API already backs it.` |

Microcopy rules:

- Use concise, domain-accurate, consequence-oriented operator language.
- Prefer nouns already locked by prior phases: `DCR onboarding`, `DCR policy`, `post-logout redirect URIs`, `logout propagation URIs`, `registration access token`, `initial access token`, `refresh family`, `logout deliveries`.
- Avoid fear language and generic security-dashboard wording such as `threat center`, `attack map`, `military-grade`, `lock it down`, or decorative shield/lock tropes.
- Preserve journey psychology: Orient answers what needs attention, Configure answers what posture should change, Support answers what happened to an account/client/token/grant, and Operate answers what live protocol work is waiting or failing.

## Route And Workflow Inventory Contract

The Phase 116 route/workflow inventory must be source-derived, not screenshot-derived.

| Rule | Contract |
|------|----------|
| Route source | Derive normal mounted routes from `Lockspire.Web.AdminRouter` `live("...")` declarations. Map `live("/")` to `/admin`; prefix every other router path with `/admin`. |
| Query workflow exception | Append `/admin/clients/:client_id/edit?workflow=logout-propagation` as an operator-visible workflow exception. Treat it as URL/query state in `ClientsLive.Show`, not as a Phoenix router route. |
| Canonical path display | Publish operator-readable `/admin...` paths. Do not include host-specific mount prefixes such as `/lockspire/admin` as canonical route truth. |
| Row shape | Every route/workflow row must include journey, persona, JTBD, entry point, primary decision, primary action, empty state, risk state, follow-up route, evidence, and surface classification. |
| Surface classification | Use exactly `admin_supported`, `demo_only`, `test_only`, or `internal_lab`. Lab/demo evidence must never become an accidental public support claim. |
| Operation queues | Logout, interaction, and device authorization queues remain truthful about read-only support unless existing domain APIs back an action. Do not add retry/discard controls in Phase 116. |

Minimum route groups:

- Orient: `/admin`, `/admin/overview`.
- Configure: `/admin/clients`, client detail/edit/redirect/logout/PAR/security/credential/RAT workflows, `/admin/policies`, `/admin/policies/par`, `/admin/policies/security-profile`, `/admin/policies/dpop`, `/admin/policies/dcr`, `/admin/keys`, `/admin/keys/:id`, `/admin/dcr`, `/admin/iats`, `/admin/iats/new`.
- Support: `/admin/consents`, `/admin/consents/:id`, `/admin/tokens`, `/admin/tokens/:id`.
- Operate: `/admin/interactions`, `/admin/device_authorizations`, `/admin/logouts`.
- Required workflow exception: `/admin/clients/:client_id/edit?workflow=logout-propagation`.

## Visual And UX Rubric

The Phase 116 rubric must use these pass/fail gates.

| Gate | Contract |
|------|----------|
| Architectural structure | Admin screens should read as structured trust: clear panes, rows, lifecycle groups, and workflow shells. Do not use decorative security-console tropes. |
| Restrained Signal Cyan | Signal Cyan is role-bound to dark/hero/focus/non-text accents. Light-mode text/actions use contrast-safe Deep Cyan. |
| Calm operator hierarchy | Every route states page job, primary decision, next safe action, empty state, and risk state without anxious or generic copy. |
| Light/dark/system parity | System is default; light and dark are first-class. Dark mode remaps semantic aliases only. |
| No generic security tropes | Reject generic shields, locks, threat maps, neon overload, blue/purple template dashboards, and fear-led language. Use Lockspire's faceted/architectural identity. |
| Accessibility floor | Visible focus, keyboard reachability, non-color status cues, AA contrast, accessible labels/descriptions, no duplicate IDs, reduced-motion safety. |
| Responsive floor | No page-level overflow at narrow widths. Long URLs, identifiers, scopes, and token handles must wrap or use `long_value` patterns. |
| Redaction floor | No plaintext client secrets, registration access token plaintext, initial access token plaintext after creation, refresh/access token plaintext, authorization codes, cookies, private keys, verifier material, user codes, or unredacted sensitive values in fixtures, screenshots, logs, docs, or lab states. |
| Destructive floor | Destructive actions must name the durable consequence and require existing confirmation treatment. Phase 116 records gaps; it does not add new destructive behavior. |

## Inventory Lab Scope

| Scope Item | Contract |
|------------|----------|
| Purpose | Test Lockspire's admin design system against real route/component states and hostile data shapes without creating a new supported surface. |
| Allowed | ExUnit-rendered HEEx/function components, repo-local fixture modules, demo-only fixture data, maintainer screenshots in later phases, source-derived route/component inventory tests. |
| Classification | `internal_lab`, `test_only`, or `demo_only`; never `admin_supported`. |
| Disallowed | Mounting through `Lockspire.Web.AdminRouter`, public admin route, public API, public docs support promise, PhoenixStorybook in Phase 116, React/JS Storybook shell, public theming engine, host-editable registry, new runtime OAuth/OIDC behavior. |
| Fixture safety | Use hostile but redaction-safe data: long URLs, long client IDs, dense scopes, disabled actions, destructive confirmations, empty/error states, status clusters, copy-once panels with safe placeholders only. |
| Proof shape | Phase 116 proof should be ExUnit/source contracts first. Browser/screenshot evidence becomes mandatory in later CSS/component/page phases. |

PhoenixStorybook is explicitly rejected/default-deferred for Phase 116. It remains a future option only if the lightweight Lockspire-owned lab becomes too bespoke or the component API grows beyond current admin UI needs.
