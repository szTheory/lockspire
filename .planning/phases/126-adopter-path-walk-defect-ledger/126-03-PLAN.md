<objective>
Build the stdlib-only HTTP flow driver that completes the documented authorization-code + PKCE
sequence against the booted host app, and that proves the issued access token is *usable* at two
independent layers.

Purpose: ADOPT-04 requires the walk to assert that the flow actually issued a usable token, not
merely that each command exited zero. `<mount>/userinfo` alone is insufficient because it is
Lockspire-owned on both ends — a regression in the resource-server acceptance path would pass there
while every real adopter's API route rejected the same token (D-29). The second layer is what makes
the claim real.

Output: `scripts/maintainer/adopter_path_flow.py` and
`test/lockspire/maintainer/adopter_flow_driver_contract_test.exs`.
</objective>

Imports are restricted to the standard library: `base64`, `hashlib`, `http.client`, `json`, `os`,
`re`, `sys`, `time`, `argparse`, `http.cookies.SimpleCookie`, and
`urllib.parse.{parse_qs, urlencode, urljoin, urlparse}`. No third-party package may be imported.

Configuration comes from `argparse` with environment fallbacks: `--base-url` (default
`http://127.0.0.1:4200`, also readable from `LOCKSPIRE_WALK_BASE_URL`), `--mount` (default
`/lockspire`), `--client-id` (default `adopter-walk-public`), `--email`, `--password`,
`--protected-path` (default `/api/walk/summary`), and `--scope` (default
`openid email profile read:walk`). Keep the `.rstrip("/")` normalisation on the base URL.

Copy the `Browser` class verbatim in shape: per-instance cookie jar, `request(method, target, data,
headers, follow)` with the eight-hop redirect chaser that downgrades to GET on 303 or on a non-GET
method, `_single_request` building `application/x-www-form-urlencoded` bodies from dicts and
harvesting `set-cookie` into the jar. Copy `assert_status`, `assert_contains`, `assert_equal`,
`location`, `json_body` and `code_challenge` verbatim, keeping the 600-character body truncation
budget in error details.

Replace the CSRF scrape rather than copying it. The demo's pattern requires the value attribute to
follow the name attribute immediately, which misses LiveView output — LiveView renders the attributes
as name, then type, then a bare hidden flag, then value, so the naive pattern silently misses and the
POST returns 403 (D-25, confirmed empirically during research). Implement `csrf(body, label)` with a
two-pattern fallback chain: first a form-input pattern that tolerates intervening attributes between
the name and the value, then a `<meta name="csrf-token" content="…">` pattern, which the stock
generated root layout renders and which `protect_from_forgery` accepts. Raise an `AssertionError`
naming the label when neither matches. The fallback exists because Lockspire's shipped `ConsentLive`
emits no form token at all — that absence is a defect the ledger records, not something to work around
silently, so annotate the fallback branch with the comment token
`# LOCKSPIRE_WALK_WORKAROUND: ADOPT-D10`.

`wait_until_ready(base_url, mount)` polls `GET <mount>/.well-known/openid-configuration` until it
returns 200 or a 45-second deadline expires, then additionally requires `GET <mount>/jwks` to return
at least one key before the flow proceeds. The JWKS precondition is deliberate: RESEARCH Open Question
1 is unresolved on whether `Lockspire.Admin.generate_key/1` alone yields a published, active key, and
an empty JWKS must surface here as a named readiness failure rather than as an opaque signing error
later.

`login(browser, email, password)` GETs `/users/log-in`, asserts 200, scrapes the CSRF token, and POSTs
`_csrf_token` plus `user[email]` and `user[password]`. The parameter nesting is mandatory: the
generated session controller pattern-matches on a nested `"user"` map and the login LiveView builds
its form with an `as: "user"` option, so flat parameters produce a function-clause error or a bounce
back to the login page (Pitfall 7).

`exercise_authorization_code(...)` drives the sequence: build a PKCE verifier and its S256 challenge;
`GET <mount>/authorize` with `response_type=code`, the client id, the redirect URI, the scope, a state,
a nonce, `prompt=consent`, `code_challenge` and `code_challenge_method=S256`; expect a 302 handoff and
parse `interaction_id` and `return_to` out of its location; call `login(...)` and expect a 302. Then
navigate to the captured `return_to` value with an explicit `browser.request("GET", return_to)` — do
not append it as a query parameter to the login POST. The generated `log_in_user/3` redirects to a
session key that only a GET through `require_authenticated_user` ever writes, so a `return_to` query
parameter on the login endpoint is inert (Pitfall 7). Annotate that explicit navigation with
`# LOCKSPIRE_WALK_WORKAROUND: ADOPT-D14`. Follow the interaction resume redirect, GET the consent page
and assert 200, then POST `<mount>/interactions/<interaction_id>/complete` with the scraped CSRF token
and `decision=approve`. Expect a 302 to the callback; assert the callback path equals the registered
redirect URI and that `state` round-tripped, then capture `code`. Finally POST `<mount>/token` with
`grant_type=authorization_code`, the client id, the redirect URI, the code and the `code_verifier`,
assert 200, and assert the response body carries a non-empty `access_token` and a non-empty
`id_token`. An absent or empty `access_token` is a failure of this step, never a pass.

Result reporting is the boundary contract with the shell harness: print one line per step in the
harness's own accumulator shape — `[PASS] step-07-flow: §6 prove the flow: <detail>` or
`[FAIL] step-07-flow: §6 prove the flow: <detail>` — on stdout, in fixed step order. `main()` catches
`AssertionError` per step so a failure in `step-07-flow` still lets `step-08-token-proof` report why it
could not run, then exits non-zero if any step reported FAIL. Never print the access token, the ID
token, the authorization code, the session cookie, or the password into a result line; print the
assertion label and the HTTP status instead.

Extend `scripts/maintainer/adopter_path_flow.py` with `exercise_token_proof(...)`, reported as
`step-08-token-proof` in the same result-line shape. It runs three assertions in this fixed order, and
the order is part of the contract because the negative case must be established before a positive
result can count as proof:

First, layer (a): `GET <mount>/userinfo` with an `Authorization: Bearer <access_token>` header on the
same browser. Assert 200, parse the JSON body, and assert it carries a non-empty `sub` plus the claim
the host's `AccountResolver` emits (the seeded user's `email`). This layer is free because userinfo is
already inside the forwarded router, but it is not sufficient on its own — it is Lockspire-owned on
both ends (D-29).

Second, layer (b) negative: construct a **fresh cookie-less** `Browser` and `GET` the protected host
path with no `Authorization` header. Assert 401. A protected route that answers anonymous callers is
not protected, and asserting the positive case without this one would let a misconfigured pipeline
read as success.

Third, layer (b) positive: construct another **fresh cookie-less** `Browser` and `GET` the same
protected host path with the `Authorization: Bearer <access_token>` header. Assert 200 and assert the
response body reflects fields the host route reads from `conn.assigns.access_token` — at minimum the
subject and the granted scope. The cookie-less browser is what makes the 200 attributable to the
bearer token alone rather than to a surviving session.

`main()` runs readiness, then `exercise_authorization_code`, then `exercise_token_proof`, prints the
per-step result lines in that fixed order, and exits non-zero when any step reported FAIL. If
`step-07-flow` failed and no access token exists, `step-08-token-proof` must report FAIL naming the
missing precondition rather than being skipped silently — an unreported step is exactly the
self-certification this phase exists to eliminate.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| driver → booted host app over HTTP | untrusted-shaped input crosses here in both directions; the driver holds real credentials and a real bearer token |
| driver process → maintainer's terminal and logs | assertion details are printed where a human and, later, CI can read them |
| anonymous caller → protected host API route | the access-control boundary ADOPT-04 exists to test |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-126-13 | Information Disclosure | driver result lines and assertion details | high | mitigate | result lines carry the assertion label and HTTP status only; bodies are truncated to 600 characters; the access token, ID token, authorization code, session cookie and password are never printed |
| T-126-14 | Spoofing | PKCE challenge generation | medium | mitigate | S256 only, via `hashlib.sha256` plus URL-safe base64 with padding stripped; the `plain` method is never sent |
| T-126-15 | Elevation of Privilege | protected host route bearer assertion | high | mitigate | the anonymous-401 case is asserted before the bearer-200 case, and both use a fresh cookie-less `Browser`, so a surviving session cannot be mistaken for token acceptance |
| T-126-16 | Tampering | CSRF token handling on the consent POST | high | mitigate | scrape a real token from the rendered page through the form-input then meta-tag fallback chain; never disable `protect_from_forgery` or forge a token to make the POST succeed |
| T-126-17 | Repudiation | a step that neither passes nor reports | high | mitigate | `step-08-token-proof` reports FAIL naming its missing precondition when `step-07-flow` did not yield a token; no step is silently skipped |
| T-126-18 | Session hijacking | driver cookie jar | low | accept | the jar is per-process, held in memory, never written to disk, and discarded when the driver exits |
</threat_model>
