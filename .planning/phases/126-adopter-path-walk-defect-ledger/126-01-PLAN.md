<objective>
Build the walk harness's end-to-end skeleton and its clean-room generation steps: one command
(`mix adopter.walk`) that parses flags, hard-fails on missing prerequisites, generates a stock
Phoenix 1.8.9 host app with `phx.gen.auth` and a password-capable user, records per-step results
with resume markers, and prints an accumulated report ending in a single pass/fail verdict.

Purpose: ADOPT-01 requires one command and one verdict; ADOPT-02 requires the host app be the stock
app a real adopter would generate; ADOPT-03 requires per-step attribution and resumability. This plan
proves that architecture end-to-end before any documented adopter-path step is layered on.

Output: `scripts/maintainer/adopter_path_walk.sh`, the `adopter.walk` alias,
`test/lockspire/maintainer/adopter_walk_contract_test.exs`, and a `/.harness/` gitignore entry.

Strict mode is `set -uo pipefail` — deliberately without the abort-on-error option, because D-18

Flags, following `repo_hygiene_check.sh`'s `usage()` heredoc plus `while [[ "$#" -gt 0 ]]` case

`--from-step NN`, `--keep`, `--force`, `--port N` (default `4200`), `--preflight-only`, `-h|--help`.
Unknown arguments print usage to stderr and exit 1.

Resolve `REPO_ROOT="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"` and `cd` to it — this value
is later written verbatim into the generated host's `mix.exs` as a path dependency (D-04), and it is
the base for `MIX_ARCHIVES="$REPO_ROOT/.harness/archives"` (D-06). Export `MIX_ARCHIVES` before any
archive-touching command in the script.

Database configuration resolves in the repo's established order (D-13): `LOCKSPIRE_WALK_DB_HOST`,
`LOCKSPIRE_WALK_DB_PORT`, `LOCKSPIRE_WALK_DB_USER`, `LOCKSPIRE_WALK_DB_PASSWORD`,
`LOCKSPIRE_WALK_DB_NAME`, falling back to `PGHOST`, `PGPORT`, `PGUSER`. `LOCKSPIRE_WALK_DB_NAME`
defaults to `lockspire_adopter_walk_dev`; it must never default to `lockspire_test` or
`lockspire_adoption_demo`. The walk starts no database of its own.

`fail_prerequisite <name> <detail>` prints `[PREREQUISITE] <name>: <detail>` to stderr and exits with
a distinct non-zero code (use 2, so a prerequisite miss is distinguishable from a RED walk's 1). It
must run before any `record_result` call so a missing tool can never reach the report or the ledger
(D-14). The preflight probes, in order: `command -v` for `git`, `mix`, `python3`, `cc`, `make`
(`cc`/`make` are required by the `bcrypt_elixir` NIF `phx.gen.auth` injects — D-26); `pg_isready`
against the resolved host/port/user; a `CREATE DATABASE` capability probe against the resolved
credentials rather than only reachability (RESEARCH assumption A5); and a check that the chosen port
is not already bound. Record each successful probe with `record_result PASS "step-00a-preflight" ...`
so `--preflight-only` produces a real report.

The accumulator copies `repo_hygiene_check.sh`'s shape, reduced to two levels (D-17): a `RESULTS`
array, `PASS_COUNT`, `FAIL_COUNT`, and `record_result <level> <label> <detail>` appending
`[$level] $label: $detail`. Labels are the step ID plus the guide section, e.g.
`record_result PASS "step-04-migrate" "§4: mix ecto.migrate exited 0"`.

Resume machinery (D-19): `mark_done <step-id>` creates `<workdir>/.walk/steps/<step-id>.done`;
`step_done <step-id>` tests for it; `should_run <step-id>` returns non-zero when `--from-step` places
the step before the resume point, or when the marker exists and `--force` was not passed — in the
latter case it records `PASS ... "skipped (already done)"` so a resumed run's report still accounts
for every step.

The evidence tree survives unconditionally: the workdir, the generated host app, `server.log` and the
step markers are never deleted by any code path, with or without a flag (D-20), because a
recursive-delete teardown destroys exactly the evidence ADOPT-03 requires. `--keep` therefore means
one thing only and must be documented as exactly that in `usage()`: **leave the booted host server
running after the walk finishes, so a maintainer can poke the app by hand.** Without `--keep` the walk
terminates the server it started. A surviving server keeps the walk port bound, which the preflight of
any subsequent run will reject as a prerequisite failure — so `--keep` is an explicit maintainer
opt-in for interactive inspection, never a default and never something an automated run passes. The
single `trap` in this script terminates the captured server pid on `EXIT`/`INT`/`TERM` and does
nothing else.

Report and verdict, copying `repo_hygiene_check.sh:507-521`'s printf shape: print a header line,
`printf '%s\n' "${RESULTS[@]}"`, then `Summary: %s PASS, %s FAIL`, then
`Result: adopter path is RED` with exit 1 when `FAIL_COUNT` is above zero, else
`Result: adopter path is GREEN`. The report line order is the step execution order and must be stable
across runs. `--preflight-only` returns after the preflight step and prints the same report shape.

Add the alias to `mix.exs` `aliases/0`, modelled on the `conformance.phase37` entry:
`"adopter.walk": ["cmd bash scripts/maintainer/adopter_path_walk.sh"]`. Do NOT add it to the `ci:`
alias — this walk generates an app, compiles a C NIF, downloads asset binaries, and boots a server;
wiring it into the contributor gate is Phase 130's GUARD-01 work (D-01). Add no dependencies.

Add `/.harness/` to `.gitignore` alongside `/tmp/` (D-08). `tmp/adopter-walk/` needs no new entry.

`step-00c-gen-auth`: run `mix phx.gen.auth Accounts User users --live` inside the generated app, then
`mix deps.get`. The `--live` flag is mandatory — without it the generator blocks on the interactive
"Do you want to create a LiveView based authentication system?" prompt and the harness hangs (D-22).
This is the strongest ADOPT-02 claim available: it is Phoenix's own default authentication, which is
what a real adopter with no accounts reaches for, and the installer's `account_resolver.ex` template
already reads `conn.assigns.current_scope.user`, which is exactly what this generator assigns (D-21).
`mix deps.get` pulls `bcrypt_elixir ~> 3.0`, a C NIF — this is why the Task 1 preflight probes `cc`
and `make` (D-26).

`step-00d-seed-user`: obtain a password-capable user non-interactively through `mix run -e` inside the
generated app, using the generator's own context functions in the exact order D-23 fixes:
`Accounts.register_user/1`, then `UserToken.build_email_token(user, "login")` inserted through the
host `Repo`, then `Accounts.login_user_by_magic_link/1` to confirm the user, and only then
`Accounts.update_user_password/2`. Order is load-bearing: `register_user/1` runs only the email
changeset, so a fresh registrant has a nil password hash and cannot password-login, and
`login_user_by_magic_link/1` raises on an unconfirmed user that already has a password. No mailbox
round trip is required. Do not insert into the `users` table directly — a hand-rolled insert silently
produces a password-less user.

secret-absence assertion in plan 126-06 — so they are a cross-plan contract, not a local choice. The
email is `walker@adopter.test` and the password is `walk-adopter-password-2026` (26 characters,
comfortably over the twelve-character minimum). Both are deliberately, obviously non-production; they
exist only inside the throwaway walk database and the gitignored workdir. Do not substitute different
values without updating plan 126-06's ledger secret-absence criterion, which greps for this exact
password literal.
