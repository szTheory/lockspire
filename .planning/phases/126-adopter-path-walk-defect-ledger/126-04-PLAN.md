The step writes a host implementation of the generated `AccountResolver` into the generated app — in
the generated host, never in the Lockspire library. AGENTS.md is explicit that account resolution,
claims, login redirects, branding and product policy are host-owned seams; implementing any of this
inside `lib/lockspire/` would both violate that boundary and destroy the evidence the walk exists to
produce.

`resolve_account/2` looks up the host `Accounts` context by the subject reference and returns the
account struct the protocol expects; the subject reference for this walk is the generated user's id
rendered as a string. `build_claims/2` returns the ID-token and userinfo claim map. It must emit
`email` with the seeded user's address, because that is the exact claim
`scripts/maintainer/adopter_path_flow.py` asserts at `<mount>/userinfo` — the two sides are one
contract and must be kept in sync. `current_account/1` needs no host code: it already pattern-matches
the `current_scope.user` assign that `mix phx.gen.auth --live` sets, which is the strongest evidence
that the template and the generator were designed for each other.

to implement but supplies no worked example, no subject-reference format contract, and no claim map
shape — the only guidance is the text inside the template's own raise. Record that as FAIL attributed
to the guide with provisional ledger ID `ADOPT-D11` and owning phase 128, then continue.

to the generated host's `mix.exs` application block so the host can order its own Repo first, and add
Lockspire's three supervision children — the named Oban runtime built from its runtime config, the
JWKS cache child spec, and the key cache — to the generated host's supervision tree after the host
Repo. The queue-disabling config key was already added in `step-03a-config-import` under `ADOPT-D04`;

`mix run -e 'IO.puts("boot ok")'` to succeed, and on failure capture the first error line from the

make a later assertion easier; a route that accepts any token proves nothing about ADOPT-04.
