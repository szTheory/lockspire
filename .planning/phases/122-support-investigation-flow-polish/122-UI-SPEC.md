# Phase 122 - UI Design Contract

> Visual and interaction contract for Phase 122: Support Investigation Flow Polish. Generated by gsd-ui-researcher for planner, executor, checker, and auditor use.

Phase 122 makes token and consent investigation pages read like calm support workflows instead of metadata inventories. It does not change OAuth/OIDC behavior, storage schemas, Admin API capabilities, host-owned policy, public theming, public component APIs, or maintainer-only proof boundaries.

Sources: `AGENTS.md`, `.planning/STATE.md`, `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`, Phase 107/108/109 UI specs, Phase 121 Support scorecards, `brandbook/`, `lib/lockspire/web/admin_css.ex`, `lib/lockspire/web/components/admin_components.ex`, and current token/consent LiveViews.

## Design System

| Property | Value |
|----------|-------|
| Tool | none; Phoenix function components plus embedded `lockspire-admin-*` CSS |
| Preset | not applicable |
| Component library | Lockspire-owned `Lockspire.Web.Components.AdminComponents` and existing LiveView/AdminLayout surfaces |
| Icon library | none; keep visible text labels for all Support actions and status meaning |
| Font | `--ls-font-display` Familjen Grotesk stack for headings; `--ls-font-sans` Inter stack for UI/body; `--ls-font-mono` JetBrains Mono stack for IDs, handles, timestamps, token families, and redacted values |
| CSS architecture | BEM/design-token `lockspire-admin-*`; no Tailwind, shadcn, public theming engine, host registry, or arbitrary one-off classes |

Implementation boundary:

- Use existing Admin APIs only: list/get tokens, list/get consents, revoke token, revoke token family, revoke consent. Do not add bulk actions, reveal actions, recovery actions, or unsupported mutation controls.
- Prefer existing primitives when they reduce page complexity: `page_hero`, `decision_summary`, `entity_header`, `pane`, `resource_list`, `dense_resource_row`, `long_value`, `status_badge`, `description_list`, `filter_bar`, `form_field`, `confirmation_panel`, `action_group`, `error_summary`, `error_list`, `empty_state`, `timestamp`, and `admin_button`.
- Keep LiveViews responsible for URL filters, loaded state, event handling, validation state, and Admin API results. Components render structure, hierarchy, safety treatment, and wrapping.
- Do not expose access token plaintext, refresh token plaintext, token hashes, client secrets, verifier material, cookies, authorization codes, user-code material, or unredacted account-sensitive values.

## Support Route Contract

| Route | Primary Job | Primary Decision | Primary Action | Required Follow-Up |
|-------|-------------|------------------|----------------|--------------------|
| `/admin/tokens` | Investigate token and refresh-family state by account, client, and status. | Which token lifecycle records match the incident? | Filter tokens | Link each row to `/admin/tokens/:id`. |
| `/admin/tokens/:id` | Decide whether one token or refresh family needs revocation. | Is the safe action single-token revoke or family revoke? | Review token | Link back to the filtered token investigation when possible; otherwise `/admin/tokens`. |
| `/admin/consents` | Investigate remembered and revoked grants by account, client, and status. | Which stored grants match the support case? | Filter consent grants | Link each row to `/admin/consents/:id`. |
| `/admin/consents/:id` | Decide whether one stored grant is healthy or should be revoked. | Should this durable grant remain active? | Review stored grant | Link back to the filtered consent investigation when possible; otherwise `/admin/consents`. |

Every Support page must answer, in this order:

1. Which Support workflow and selected case context am I in?
2. What health or grant state needs attention?
3. What family, scope, client, or account pivot explains the state?
4. What is the smallest safe action?
5. What consequence will that action have?

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs / `--ls-space-1` | 4px | Badge internals, required-marker gaps, tiny inline state gaps |
| sm / `--ls-space-2` | 8px | Label-to-value gaps, compact metadata stacks, dense row internals |
| md / `--ls-space-4` | 16px | Default filter, pane, row, metric, and action-cluster spacing |
| lg / `--ls-space-6` | 24px | Section/card padding, pane gaps, confirmation-panel groups |
| xl / `--ls-space-8` | 32px | Page body padding and page-hero padding |
| 2xl / `--ls-space-12` | 48px | Empty-state vertical padding and major route breaks |
| 3xl | 64px | Reserved only for rare page-level separation; do not add new Phase 122 CSS unless a no-overflow proof shows it is necessary |

Exceptions:

- Existing shipped compatibility values at 12px, 20px, and 40px may remain. Do not introduce new spacing values for Phase 122 support polish.
- Standard inputs, buttons, and button-like links keep `--ls-control-height: 40px` minimum.
- At widths below 720px, filter bars, row actions, pane headers, entity headers, dense rows, confirmation actions, and action groups stack vertically with full-width buttons.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px (`--ls-type-label-size`) | 600 | 1.2 |
| Body | 14px (`--ls-type-body-size`) | 400 | 1.5 |
| Heading | 16px (`--ls-type-heading-size`) | 600 | 1.25 |
| Display | 24px (`--ls-type-display-size`) | 600 | 1.2 |

Rules:

- New Phase 122 UI copy uses exactly these four sizes and exactly two weights: 400 and 600.
- Existing heavier shell or legacy values may remain where already shipped, but Support page edits must not expand the type scale.
- Use mono only for durable handles, token family IDs, account/client IDs, timestamps, code-like status values, and redacted placeholders.
- Long mono values must render through `long_value`, `timestamp`, or an existing class with `overflow-wrap: anywhere`.
- Page headings and pane headings use calm support language, not generic metadata labels.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--ls-surface-page`: light `#f8fafc`, dark `#0b1220` | Admin shell background and broad quiet page surface |
| Secondary (30%) | `--ls-surface-panel`: light `#ffffff`, dark `#131c2e`; plus `--ls-surface-muted` | Page heroes, panes, rows, filter bars, empty states, confirmation panels |
| Accent (10%) | `--ls-text-accent`: light Deep Cyan `#0e7490`, dark Signal Cyan `#22d3ee` | Primary CTA, current nav, resource title links, selected filter summary affordance, focus ring |
| Destructive | `--ls-status-danger-*`: light text `#991b1b` / bg `#fee2e2`; dark text `#fca5a5` / bg `#2e1517` | Revoke buttons, revoke confirmation panels, field errors, terminal security states |

Accent reserved for: `Filter tokens`, `Filter consent grants`, resource title links, active/current navigation, selected context emphasis inside summaries, and focus-visible rings. Accent must not be used for decorative panels, every badge, all links indiscriminately, or normal body text.

Status semantics:

| Status | Contract |
|--------|----------|
| Success / healthy | Active grants, active tokens, completed support facts. |
| Warning / waiting | Attention-worthy but not terminal context, including pending or partial family pressure when introduced. |
| Danger | Reuse detected, revoked when incident-worthy, destructive confirmation, validation/error state. |
| Disabled / closed | Expired or already revoked states when no further action is available; copy must still say what is closed. |
| Info / provenance | Grant kind, token type, remembered/DCR/system provenance, explanatory support context. |

Color is never the only state signal. Badges must include visible text, confirmation copy must name consequence, and error text must state the next repair path.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Token index: `Filter tokens`; consent index: `Filter consent grants`; token detail: `Review token`; consent detail: `Review stored grant` |
| Empty state heading | `No investigation results match these filters` |
| Empty state body | `Adjust the account, client, status, or scope filters, or return to the overview to choose a different Support workflow.` |
| Error state | `Investigation context could not be loaded. Check the selected account, client, status, or identifier, then reload this Support workflow.` |
| Destructive confirmation | `Revoke token`: confirm only this token and name token type, client, subject, expiration, and effect. `Revoke token family`: confirm family-wide refresh-token invalidation and name family, client, subject, active-token count when available, and irreversibility. `Revoke consent grant`: confirm remembered-consent consequence and name client, subject/account, scopes, and grant status. |

Copy rules:

- Use the journey label `Support` exactly.
- Use verb-plus-noun action labels. Approved labels include `Filter tokens`, `Filter consent grants`, `Review token`, `Review stored grant`, `Revoke token`, `Revoke token family`, and `Revoke consent grant`.
- Do not add generic labels such as `Submit`, `Apply`, `OK`, `Open`, `Go`, `Continue`, `Manage`, or one-word `Revoke`.
- Error copy must avoid backend leakage and secret values. It must say what context failed and what the operator should do next.
- Already-revoked copy must be calm and final: `This token is already revoked. No further token action is available.` or `This consent grant is already revoked. It no longer authorizes future remembered-consent reuse.`
- No copy may imply Lockspire can recover plaintext tokens, token hashes, secrets, host account policy, or host-owned user data.

## Page Composition Contract

### Token Index

- Lead with `page_hero` using eyebrow `Support`, title `Token investigation`, and selected account/client/status summary.
- Add or preserve a compact `decision_summary` immediately after the hero or inside the main support pane with exactly these items: `Selected filters`, `Token health`, `Family pressure`, and `Smallest safe action`.
- Use `filter_bar` with `form_field` wrappers for account, client, and status. If scope/date filters are added later, they must remain URL-owned and visible in the selected-filter summary.
- Rows should use `dense_resource_row` when metadata density increases. A row must lead with health/status and support context before raw identifiers.
- Each token row must expose, without plaintext or hashes: token type, status, redacted client handle, redacted account handle, redacted family handle, expiry or last lifecycle timestamp, and `Review token`.
- Metrics or summaries must include active, revoked, expired, reuse detected, total matching, and selected filter context when data is available.
- The index must not render revoke, family revoke, bulk revoke, reveal-token, edit-token, or recovery controls.

### Token Detail

- Lead with `page_hero` and `entity_header`; the first decision must be token health and smallest safe action, not the token handle.
- Add a `decision_summary` before long description lists with exactly these items: `Token health`, `Family lineage`, `Reuse pressure`, and `Smallest safe action`.
- Keep identity/history data in panes: `Token identity and current state`, `Refresh family lineage`, and `Corrective actions`.
- Family lineage rows use `dense_resource_row` and `long_value`; current token, generation, active count, revoked count, and reuse signal must be scannable before lesser metadata.
- Corrective actions must present single-token revoke before family revoke. The family action must visually and textually read as broader and more consequential.
- Already-revoked or no-family states must disable or de-emphasize impossible actions and explain why. A disabled button must use existing disabled semantics (`disabled` or `aria-disabled`) rather than looking active.

### Consent Index

- Lead with `page_hero` using eyebrow `Support`, title `Consent grant investigation`, and selected account/client/status summary.
- Add or preserve a compact `decision_summary` with exactly these items: `Selected filters`, `Grant status`, `Scope context`, and `Smallest safe action`.
- Use `filter_bar` with `form_field` wrappers for account, client, and status. If scope filtering is added later, selected scope must appear in the summary and empty-state copy.
- Rows should use `dense_resource_row` when metadata density increases. A row must expose grant status, client, redacted account, scope summary, updated/revoked timestamp, and `Review stored grant`.
- The index must not render revoke, bulk revoke, edit grant, reveal secret, or unsupported recovery controls.

### Consent Detail

- Lead with `page_hero` and `entity_header`; the first decision must be whether the grant remains active, not a raw grant identifier.
- Add a `decision_summary` before long description lists with exactly these items: `Grant status`, `Scope context`, `Client/account pivot`, and `Revocation consequence`.
- Keep identity/history data in panes: `Durable grant identity and current state`, `Scope context`, and `Revoke consent grant`.
- Scope context must remain readable under long and dense scope lists; use `long_value` or equivalent wrapping.
- Revocation must clearly say it stops future remembered-consent reuse; it must not imply host account changes, session termination, or token revocation unless an existing domain API actually performs that behavior.
- Already-revoked state must render closed-state copy and disabled/de-emphasized action semantics.

## Confirmation And Error Contract

| Surface | Required Pattern |
|---------|------------------|
| Revoke token | `confirmation_panel` variant `:danger`, one checkbox, non-secret resource summary, visible error list/summary on missing confirmation, button label `Revoke token` or disabled `Token already revoked`. |
| Revoke token family | `confirmation_panel` variant `:danger`, one checkbox, non-secret family/client/subject summary, active count when available, clear family-wide consequence, button label `Revoke token family` or disabled `Token family already revoked`. |
| Revoke consent grant | `confirmation_panel` variant `:danger`, one checkbox, client/account/scopes summary, remembered-consent consequence, button label `Revoke consent grant` or disabled `Consent grant already revoked`. |

Rules:

- Confirmation forms must use consistent checkbox pattern, `phx-submit`, visible labels, and action-specific error copy.
- Confirmation errors must render through `error_summary`, `error_list`, or existing field/error classes with `role="alert"` where appropriate. A plain paragraph is not sufficient after Phase 122 polish.
- Error copy must preserve state truth: if revocation fails, state that the token/grant may still be active and the operator should reload or retry the Support workflow.
- Notices must distinguish `already revoked` from `just revoked` and must avoid implying plaintext recovery or host-account changes.

## State Coverage Contract

| State | Required UI Treatment |
|-------|-----------------------|
| Empty true-zero | Specific empty heading plus next Support route or overview pivot. |
| No-match filters | `No investigation results match these filters` plus selected filter summary and filter adjustment path. |
| Active | Success/healthy badge plus current safe action. |
| Revoked | Closed or danger badge depending context; no active-looking destructive CTA. |
| Expired | Closed/disabled badge plus copy that no active token remains because of time. |
| Reuse detected | Danger badge and summary item; family revoke consequence must be visible before metadata. |
| Long identifiers | `long_value` or equivalent wrapping for account, client, token, family, grant, scope, and timestamp values. |
| Dense results | Summary first, then dense rows; avoid raw table as the primary experience. |
| Validation/error | Specific error copy, no backend leakage, no secret values, accessible alert/error semantics. |
| Already revoked | Closed-state notice, disabled/de-emphasized action, and no repeated active mutation affordance. |

## Responsive And Accessibility Contract

- At 320px, 390px, 768px, 1024px, and 1440px, touched Support pages must not require page-level horizontal scrolling.
- Below 720px, Support rows stack in this order: title/decision, status cluster, support context, long values, metadata, actions.
- Filter controls stack to one column below 720px, with selected-filter summary still visible above the row list.
- Confirmation panels stack after state summaries on mobile. Destructive actions must not visually precede the state/consequence copy.
- Focus rings remain visible on nav links, filter fields, row links, review buttons, checkboxes, revoke buttons, and back links.
- Status meaning never relies on color alone; badge text and consequence copy are required.
- Reduced motion keeps hover/focus feedback but neutralizes active transforms through the existing `prefers-reduced-motion` behavior.
- No icon-only actions are approved for this phase.

---

## Security And Redaction Contract

- Never render access token plaintext, refresh token plaintext, token hashes, client secrets, verifier material, cookies, authorization codes, user-code material, or raw sensitive account identifiers in HTML, logs, docs, screenshots, fixtures, flash copy, notices, or error text.
- Continue using `Redaction.handle/2` or existing redacted handles for account, client, consent grant, token, and family pivots.
- Support pages may show durable non-secret metadata only: redacted handles, statuses, token type, grant kind, scopes, timestamps, generation counts, family counts, and existing Admin API display names.
- Do not create copy-to-clipboard, reveal, decode JWT, inspect hash, export, bulk action, or raw audit dump controls.
- Screenshot/manual proof must use redaction-safe demo values that stress long wrapping without resembling real tokens or secrets.
