State the rule in bold: never remove an old KEK before `--check` passes, and keep it in your secret manager for as long as you keep backups written under it.

    Warnings (D-14), each as its own short subsection at full strength:
    - Backup remanence: backups, WAL archives, replicas, snapshots and dumps taken before re-encryption still hold usable plaintext private keys. Expire them, or after the switch to `:reject` generate new signing keys and retire the previously plaintext ones; that is the only full remedy.
    - Rollback: earlier versions cannot read envelopes and there is no decrypt task. Before the switch, roll back by setting `legacy_plaintext: :allow`, never by removing the key-encryption config.
    - KEK loss: if every configured KEK is lost, the signing keys cannot be recovered; generate new keys, and tokens signed by the old keys stop verifying once those keys leave the JWKS.
    - Separate KEK backup: quote the GitLab principle that storing encrypted information in the same location as its key defeats the purpose; never keep the KEK in the same backup as the database.

    Operational hygiene (D-14, D-06): a crash dump can contain `:persistent_term` values and the memory of every process, which includes Lockspire's decoded key-encryption keys; application env itself is not written to the dump, but anything that read the key into a process is. Restrict dump file permissions and location, or set `ERL_CRASH_DUMP_SECONDS=0` (or `ERL_CRASH_DUMP_BYTES=0`) where policy forbids dumps. The raw KEK stays in application env, so anyone with a remote shell or Observer access can read it. Never list `LOCKSPIRE_KEY_ENCRYPTION_KEY` in LiveDashboard `env_keys`. Add a conditional sentence about database statement logging only after checking postgresql.org (see context); drop it if the claim does not hold.
