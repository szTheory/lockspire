<objective>
Close INSTALL-03's core: today `Install.run/1` writes files one at a time and raises on the first
one that differs, then writes the manifest afterwards. A conflicted re-run therefore writes some
files, aborts mid-loop, and never writes the manifest — leaving exactly the unclear half-installed
state the requirement names verbatim. RESEARCH reproduced it: after an abort, the account resolver,
the interaction handler, and the manifest were all missing, and only the first conflict was
reported.

Purpose: an adopter who hits this fixes one file, re-runs, hits the next, and repeats — while the
host carries a partial Lockspire install and the upgrade task reports that no install manifest
exists, which is misleading because the install *was* run.

Output: `Install.run/1` split into a side-effect-free classification pass and a separate write
pass. Any conflict prints the full refusal list and raises exactly once, having written nothing.
The pattern is copied verbatim from `lib/mix/tasks/lockspire.upgrade.ex`, which already implements
this shape in this codebase.
</objective>

  <action>
Restructure `run/1` into two explicit passes.

**Pass one classifies and writes nothing.** For each rendered template, read the destination and
map the outcome onto one of three classifications: contents byte-identical to the rendered output
is unchanged; contents present but different is a conflict; the file being absent is a create; any
other read error is a conflict carrying the inspected reason rather than an immediate raise. Byte
identity is the rule — compare the raw binaries, exactly as the current code's pattern match does
and as the manifest's sha256 does. Do not normalize whitespace or line endings; a destination that
differs only in trailing newline is a conflict, and that is the deliberate answer to the encoding
edge question of whose definition of equality applies.

Directory creation currently happens inside the per-file helper before the read. That is a write,
and it must move into pass two — the plan pass must be genuinely side-effect-free, which is what
makes the zero-bytes guarantee provable. Everything the plan pass needs is readable:
`rendered_templates/1` reads templates, and destination reads are reads.

Add a containment guard in the plan pass: each destination is already expanded, so assert it
resolves to a path inside the expanded project root. A destination that escapes is classified as a
conflict with a reason naming the escape, not written. The switch values that feed destination
construction are operator-supplied, so this is cheap insurance and it belongs in the pass that
already inspects every destination.

Use the manifest's recorded per-file checksums to make the reason useful. `lockspire.upgrade`
already performs the three-way comparison — recorded checksum versus current content versus newly
rendered content — and that is exactly what distinguishes "you edited this" from "Lockspire changed
this; run the upgrade task." Reuse it so the refusal message tells the adopter which of the two
situations they are in. When no manifest exists, fall back to reporting a host edit.

**Refusal is atomic and complete.** If pass one produced any conflict, print one line per conflicted
destination in the order the template inventory defines, in the `REFUSE <path> (<reason>)` shape
`lockspire.upgrade` uses, each followed by an indented fix line, and then raise exactly once with a
summary message. Print paths and reason phrases only — never the file's contents; the project's
redaction rule applies to operator surfaces. Accumulate by prepending and emit reversed, so the
order matches the template inventory rather than the reduce's accumulation order.

**Pass two applies.** Only reached when pass one produced zero conflicts. Create directories, write
the files that need creating, print the existing created and unchanged lines unchanged — those
exact strings are asserted by the idempotent re-run test and by the walk harness — then write the
manifest and print the instructions. Expose the two passes as named functions (`plan/1` and
`apply_plan!/2` or equivalently named) so tests and 127-08 can drive classification without writing.

Create `test/integration/install_conflict_semantics_test.exs` defining
`Lockspire.Integration.InstallConflictSemanticsTest` with `use ExUnit.Case, async: false` and
`import ExUnit.CaptureIO`. Install into the existing fixture root, then edit **two** managed
destinations rather than one, capture `tree_checksums/1` over the whole fixture root, run the
installer expecting a raise, capture `tree_checksums/1` again, and assert the two maps are equal.
Assert both edited paths appear in the captured refusal output. Assert the refusal output does not
contain the sentinel text that was written into the edited files, which proves contents are not
echoed. Add the trailing-newline case as its own test, and the escaping-destination case as its
own test. Add a test that after a refused first-ever run, no manifest exists.

Update the two assertions in `install_generator_test.exs:323-361` that pin the old first-conflict
raise message to the new refusal shape. Change nothing else in that file.
