<objective>
Replace the human who adjudicates `mix adopter.walk` with a deterministic diff, and run it in CI.

Purpose: the walk is the only thing in this repo that exercises the real adopter path end to end --
a generated `phx.new` host, a real database, a real booted server, a real authorization-code plus
PKCE flow. Nothing in CI or the test suite runs it; the three maintainer contract tests only grep
its source. That gap is measured, not theoretical: CI was fully green while all twelve ledger
defects were live. Today its verdict is a human reading a thirty-one line report and comparing it
by eye, which is what blocks 127-09 Task 3 and which phases 128 and 129 each need again.

The constraint that shapes the whole design: the walk is expected to be RED while defects remain.
`126-DEFECT-LEDGER.md` forbids any gate asserting it exits 0. So the gate is "actual matches the
recorded expectation" -- which is also what keeps the CI signal green by default instead of a red
badge everyone learns to ignore across two more phases.

Output: a machine-readable report, a hand-authored baseline committed before the run that the run
can refute, a verifier that distinguishes regression from unrecorded fix from infrastructure, four
static invariants binding the baseline to the ledger and the harness, and an advisory
paths-filtered CI lane with no schedule.
</objective>

It must NOT be a Mix task under `lib/` -- `package_files` ships `lib/**/*.ex` to Hex, so it would

Preconditions, each a hard error: `invocation.preflight_only` set, `invocation.from_step` other than
`00`, or any row with `resumed: true`. The baseline describes a full from-scratch walk, and comparing
it against a resumed run silently misattributes occurrences. This is the primary guard against a
falsely-green verifier.

Comparison over `(step_id, occurrence)` maps, with exit codes:
  - levels agree everywhere -> exit 0. The walk's own exit code is irrelevant; a RED walk matching
    its baseline exits 0. This is the ledger's inversion warning discharged mechanically.
  - expected PASS, actual FAIL -> REGRESSION -> exit 3
  - expected FAIL, actual PASS -> UNRECORDED_FIX -> exit 3
  - actual row absent from baseline -> NEW_ROW -> exit 3
  - baseline row never observed -> MISSING_ROW -> exit 3
  - walk exited 2, or report missing / truncated / wrong schema -> INFRA -> exit 2
  - count drift is reported but is never the sole cause of failure
Exit 1 is reserved for usage and precondition violations.

UNRECORDED_FIX is a hard failure, deliberately. A defect fixing itself without a ledger disposition
is the exact failure mode phases 127-129 exist to prevent, and the ledger already enforces two-way
marker equality failing in both directions -- a one-directional baseline would be strictly weaker
than the convention beside it. Word it warmly, naming the step and defect and pointing at the ledger.

Provide `--print-baseline-patch`, printing proposed rows to stdout for a human to paste and annotate.
Do NOT provide `--bless` or `--update-baseline`: that is the mechanism by which every golden-file

friction is the point.
