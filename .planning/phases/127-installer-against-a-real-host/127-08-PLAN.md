<objective>
Finish INSTALL-03. Plan 127-07 made a conflicted run atomic; this plan makes the whole re-run
surface observable and predictable: an adopter can ask what would happen without changing anything,
a mismatched re-run is caught instead of silently producing a second orphaned file set, and the
manifest stops being the one managed file that silently overwrites.

Purpose: three gaps remain. There is no way to inspect a planned install without performing it.
A re-run with different module or mount-path switches writes a whole second set of files while the
first set stays behind, because nothing compares the supplied inputs against the ones the manifest
already recorded. And `Manifest.write/2` silently overwrites a differing manifest while every other
file refuses — an inconsistency an adopter has no way to predict.

Output: a `--dry-run` switch mirroring `mix lockspire.upgrade` exactly, manifest-input drift
detection using state the manifest already records, and a manifest write that refuses on drift like
everything else. No force switch and no prompt.
</objective>

  <action>
Add an input-drift check to the plan pass. `Manifest.build/2` already records the web module, the
scope module, the mount path, the storage prefix, and the Oban prefix, so no new state is needed —
load the existing manifest, compare each recorded input against the corresponding value in the
assigns built for this run, and classify any difference as a conflict on the manifest path. The
refusal reason must name the key and both the recorded and the supplied value, because "the inputs
changed" is not actionable and the specific delta is. Without this, a re-run with different module
switches writes a whole second set of host files while the first set stays behind, orphaned and
unmanaged.

Make the comparison defensive. The manifest is decoded from JSON into a plain map, so treat a
missing inputs entry, a non-map inputs entry, or a missing individual key as a refusal that names
the manifest as unreadable — never as an unhandled crash and never as a silent pass. When no
manifest exists at all, this is a first install; there is nothing to compare and the check does not
apply.

Bring the manifest write into line with every other managed file. Today it is the lone exception:
when the on-disk manifest differs it is overwritten and an updated line is printed, while every
other differing file refuses. Classify the manifest alongside the twelve rendered destinations in
the plan pass and let the same refusal path handle it, so an adopter who edited it is told rather
than silently overruled. Keep the unchanged and created branches and their exact output strings —
the idempotent re-run test asserts the manifest's unchanged line by name.

Add tests covering: a differing web module refused with both values named; a differing mount path
refused; a malformed inputs map refused with a message naming the manifest; a host-edited manifest
refused rather than overwritten; and an identical re-run still reporting the manifest unchanged and
writing nothing. Assert zero bytes written on each refusal using the tree-checksum helper, the same
way 127-07 does.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator CLI switches → recorded install identity | module and mount-path switches determine which host files an install owns; changing them silently re-points ownership |
| on-disk manifest JSON → generator | the manifest is decoded from a file inside the adopter's repository and may be absent, edited, or malformed |
| host-owned generated files → re-run | the account resolver and consent LiveView carry host policy and must survive every re-run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-127-09 | Spoofing | manifest input drift accepted silently | high | mitigate | the plan pass compares every recorded input against the supplied assigns and refuses on any difference, naming the key and both values. Without this a re-run with different module switches produces a second orphaned file set the manifest does not track |
| T-127-29 | Tampering | host-owned generated seams during a re-run | high | mitigate | no force switch and no interactive prompt is added. A force switch would let a re-run clobber the account resolver and consent LiveView, the exact host-owned seams the phase is fenced by; a prompt would hang the non-interactive walk harness and CI |
| T-127-30 | Denial of Service | malformed or absent manifest inputs map | medium | mitigate | the comparison tolerates a missing entry, a non-map entry, and a missing key, producing a refusal naming the manifest rather than an unhandled crash |
| T-127-31 | Repudiation | manifest silently overwritten on drift | medium | mitigate | the manifest is classified alongside every other managed file, so a host edit to it is reported rather than overruled |
| T-127-32 | Information Disclosure | dry-run output | low | mitigate | the dry-run path reuses the same path-and-reason-only printing as the refusal path; no file contents are printed |
| T-127-SC | Tampering | package-manager installs | high | accept | this plan installs no packages; RESEARCH's Package Legitimacy Audit records zero new packages phase-wide and zero `[ASSUMED]`/`[SUS]`/`[SLOP]` verdicts |
