## Summary

Reviewed the full Phase 169 source scope, including install/upgrade transactions, route generation, diagnostics, host integrations, tests, and adoption guidance. The file transaction has two interruption-recovery defects: a crash window can leave a committed host file absent from the journal, and a crash during rollback cleanup can make the next recovery attempt fail permanently.

## Critical Issues

### CR-01: A file mutation can become unjournaled before a crash

**Classification:** BLOCKER  
**File:** `lib/lockspire/install/file_transaction.ex:373-384`
**Issue:** `commit_artifact/2` writes or renames the destination at line 380 and only then persists the updated `committed` list at line 381. If the process exits after the destination mutation but before the journal write completes, the on-disk journal omits that artifact. The next `recover/1` rolls back only journaled entries, so it leaves the just-created or updated host file behind. For an update this can lose the prior generated bytes and leave the manifest unchanged; the retry then refuses the changed managed file as drift. This violates the upgrade's recovery and rollback guarantee.
**Fix:** Persist a recoverable intent record atomically before mutating each destination, then mark the operation committed after the write; alternatively, synchronously undo the just-written artifact if journal persistence fails and make recovery reconcile staged intents against target checksums. Write journal replacements through a flushed temporary file and atomic rename so an interruption cannot truncate the only recovery record.

## Warnings

### WR-01: Recovery retries rollback after rollback already completed

**Classification:** WARNING  
**File:** `lib/lockspire/install/file_transaction.ex:202-209, 548-551`
**Issue:** `finalize_rolled_back/1` writes a journal with `terminal: "rolled_back"` after `rollback/1` has already restored/removed committed artifacts, then starts cleanup. If the process stops between that journal write and cleanup, the next `recover_journal/2` ignores the terminal marker and invokes `rollback/1` again. For a created artifact, the target is now absent, so the checksum check fails with `:created_target_changed`; recovery returns `:recovery_required` and normal install/upgrade retries remain blocked even though rollback completed.
**Fix:** Validate and handle the terminal state during recovery: for `terminal: "rolled_back"`, skip rollback and finish cleanup. Another safe option is to persist a terminal journal with an empty committed list only after rollback has completed.
