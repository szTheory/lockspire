LOCKSPIRE MILESTONE GUIDE
Reusable intent for choosing and delivering future milestones

PURPOSE

Use this guide alongside the live GSD project state whenever evaluating a new
Lockspire milestone. It captures the durable intent behind the original
"raise the bar" prompt and adapts it to Lockspire's product, evidence, and
release model. It is a decision aid, not authorization to start every listed
candidate or to expand the product boundary.

CORE INTENT

Build the most trustworthy, useful embedded OAuth/OIDC provider library for
Phoenix and Elixir teams. Improve it with deliberate, evidence-backed work:
make adopter paths easier, protocol and security behavior more dependable,
operator tasks clearer, and maintenance and release work more repeatable.
Prefer elegant, understandable, self-documenting solutions, high-signal
automation, and durable findings with provenance. Spend effort where it
changes a real adopter or maintainer outcome; do not churn for activity,
checklist breadth, or theoretical completeness.

PRODUCT BOUNDARIES

- Lockspire is a companion library embedded in the host Phoenix application,
  not a required standalone authorization service.
- The host owns account resolution, login UX, layouts, branding, and
  product-specific policy. Keep these seams explicit and narrow.
- Keep protocol core, storage, generators, Plug/Phoenix integration, and
  LiveView/admin surfaces strongly bounded.
- Keep v1 focused on OAuth/OIDC provider needs. Do not expand into SAML,
  LDAP/AD federation, hosted auth, a generic API gateway, or a full CIAM suite.
- Preserve the shipped public contract and security posture. In particular:
  require PKCE S256 by default; exact-match redirect URIs; hash client secrets
  at rest; make authorization codes short-lived and single-use; rotate refresh
  tokens and revoke the family on reuse; and disallow implicit flow and
  alg=none.
- Treat docs/supported-surface.md, executable repo proof, current GSD state,
  and current release truth as stronger than stale strategic notes or memory.

WHO WE SERVE

Use these roles as lenses when assessing a candidate. Do not turn them into
unbounded industry-specific feature lists. Focus on shared needs and on
meaningful differences in trust, tenancy, traffic, compliance, and operations.

1. Phoenix SaaS adopter: installs Lockspire in an existing app and needs a
   clear, low-friction path through configuration, migrations, routes, login,
   consent, claims, and first-client setup.
2. Host application architect: needs stable boundaries, understandable APIs,
   predictable Ecto/Phoenix integration, upgrade paths, and no hidden service
   or infrastructure requirement.
3. Security and protocol reviewer: needs standards-aligned behavior, secure
   defaults, explicit trust decisions, negative-path coverage, and honest
   support/conformance claims.
4. Operator or support engineer: needs safe, redacted workflows to configure
   clients and keys, investigate consent/token issues, and understand lifecycle
   state without requiring source access.
5. Integrator building a client or resource API: needs interoperable discovery,
   token validation and lifecycle behavior, precise error handling, and
   executable examples.
6. End user or account holder: needs the host's familiar login and consent
   experience, with Lockspire not taking ownership of their account or UX.
7. Library maintainer and release owner: needs readable code, trustworthy CI,
   bounded dependencies, reproducible evidence, clear upgrade/release steps,
   and a repository left in an intentional state.

Consider B2B and B2C SaaS, multi-tenant products, developer platforms, and
regulated or high-trust domains as usage contexts. Their common denominator is
reliable embedded provider behavior with explicit host ownership. Pursue a
specialized requirement only when adopter evidence and a scoped acceptance
case justify it; never imply compliance or certification from a test suite.

MILESTONE SELECTION LOOP

Use the normal GSD ceremony for every new milestone. Start with
$gsd-new-milestone and preserve its goal/version confirmation, research choice,
requirements definition, roadmap approval and commit gates. Existing research,
candidate rankings and proposal phase lists are inputs, not substitutes for
that workflow. Then use the configured discuss/plan/check/execute/verify/review
steps and GSD milestone audit/closeout. Do not implement a proposal directly or
treat its lettered build stages as approved GSD phases. This applies equally to
security work and UI quality work (owner reaffirmed 2026-10-25).

Before opening a milestone:

1. Establish the real baseline from the current branch, GSD artifacts,
   supported-surface contract, tests and workflows, release records, and
   adopter/support evidence. Record sources and exact revisions where useful.
2. Separate release-train maintenance from feature work. Patch-eligible fixes,
   narrow support-truth corrections, and release hygiene stay on the normal
   train unless they materially widen the public contract. Follow
   DEVELOPMENT-TRAIN.md and RELEASE-TRAIN.md.
3. Generate candidate wedges from demonstrated friction, security or
   interoperability findings, install and upgrade gaps, operator burden, or
   repeated maintainer toil. Consider engineering quality dimensions broadly:
   correctness, security, compatibility, usability, accessibility, reliability,
   performance, operability, testability, maintainability, documentation,
   dependency health, and release integrity. Select only dimensions tied to
   evidence and a measurable user outcome.
4. Rank candidates by user impact, trust/risk reduction, frequency, evidence
   strength, leverage, and cost. State why the candidate is next, what proof
   would show success, what is explicitly out of scope, and what should be
   deferred. Prefer a thin vertical adopter journey over disconnected cleanup
   or speculative breadth.
5. Use research, standards, code inspection, and ecosystem evidence before
   asking the user to choose among technical options. Escalate decisions that
   materially change product boundaries, public API shape, security posture,
   support claims, or hard-to-reverse strategy.
6. Keep a near-, mid-, and long-horizon candidate list, but refresh it at each
   milestone close. Candidates are hypotheses with provenance and triggers,
   not promises. Re-rank against current evidence and mark shipped, obsolete,
   deferred, or rejected items instead of carrying stale lists forward.
7. If no candidate clearly improves the intended adopter story or reduces a
   material risk, choose sustainment or stop. There is no quota to create a
   feature milestone.

UPSTREAM RESEARCH AND DECISION POSTURE (USER DIRECTION 2026-10-24)

- Maintain a rolling, chunked milestone direction so a new session can resume
  from prior reasoning. Refresh stale hypotheses at each start/close; mark
  shipped, obsolete, rejected and deferred candidates with reasons and source.
  Plan the selected milestone in detail and later candidates only to the depth
  needed to preserve direction and decision triggers.
- Before downstream fan-out, enumerate consequential decisions, dependencies,
  uncertainty and acceptance. Use relevant lenses: adopter/client/host,
  product, security/protocol, architecture/storage/distributed systems,
  operations/CI and maintenance. Use UI/design lenses for actual UI scope;
  avoid unrelated specialties and generic checklists.
- Research primary standards and official ecosystem sources where they can
  settle a real question. Compare alternatives, pros/cons, concrete examples,
  established patterns, footguns and prior lessons; include an adversarial
  pass. Label facts, inferences and proposals with date/revision and limits.
- Synthesize one coherent recommended decision set, not incompatible menus
  for downstream agents. Within the user's selected scope, resolve routine
  implementation choices autonomously. Escalate only unresolved decisions
  that materially change security, public API/support, product boundaries or
  hard-to-reverse strategy; do not add ceremonial permission loops.
- Fan out independent questions to focused agents when authorized, with
  explicit ownership and one integrator. Sequence coupled decisions. Stop
  additional research/review when it no longer changes scope, risk controls,
  acceptance or ordering. Prefer a targeted reproducer to another broad survey.
- Spend planning effort upstream where it avoids rework; do not produce
  speculative detailed plans for future milestones or force empty phases when
  evidence disproves their premise. No guarantee of a perfect one-shot result
  substitutes for verification.

DEPENDENCY POSTURE (USER DIRECTION 2026-10-24)

Prefer a small, auditable local helper or limited attributed code copy over
another dependency when it reduces total complexity and maintenance. Keep
dependency trees small and flat. A necessary maintained package is welcome
when correctness/capability benefits justify its direct/transitive cost,
security history, license, updates and ownership. Record that comparison for
nontrivial additions. This is not a directive to vendor crypto, TLS, security
parsers or other complex primitives; reuse vetted existing dependencies and
OTP/framework capabilities rather than inventing a security implementation.

QUALITY AND EVIDENCE BAR

- Define outcomes in terms of what an adopter, operator, integrator, or
  maintainer can demonstrably do after the milestone.
- Prefer simple, cohesive, idiomatic Elixir and Phoenix design. Remove
  duplication and dead complexity when it is part of the chosen outcome; do
  not launch broad refactors without evidence.
- Add or change tests only to prove the milestone's actual acceptance criteria.
  Use adversarial and property-based testing where invariants and input spaces
  benefit from them. Keep fixtures realistic and safe; do not add a test tool
  or synthetic "digital twin" system without a concrete decision or failure
  mode it will improve.
- Make CI efficient and high-signal. Avoid redundant jobs and gates that do
  not catch a distinct failure class. Keep required acceptance separate from
  supplemental or exploratory conformance evidence.
- Keep examples, install generators, docs, support claims, and runtime behavior
  aligned. Redact secrets and personal data in logs, fixtures, reports, and
  durable planning artifacts. Never copy personal details from prompts into
  the repository.
- Preserve provenance for important findings: source, date/revision, observed
  behavior, disposition, and acceptance evidence. Distinguish fact, inference,
  and proposal. Do not rewrite historical receipts to make current status look
  cleaner.

MILESTONE DELIVERY AND CLOSEOUT

- Plan a coherent, bounded outcome with explicit exclusions and a verification
  path. Split work into phases only when that makes dependencies and review
  clearer.
- Keep code comments useful to maintainers; do not leave GSD orchestration,
  temporary plan, or generated workflow chatter in product code or user-facing
  output.
- Keep documentation accurate and update maintained records when the shipped
  behavior or support contract changes.
- Close the milestone with verification, review/audit, and the gates required
  by the current repo policy. Resolve or explicitly disposition failures and
  warnings; do not claim success on partial evidence.
- Leave the branch, worktrees, generated artifacts, planning state, PR, and
  release records intentional and tidy. A milestone should be release-ready.
  Actual publication still follows the milestone PR, Release Please, protected
  exact-ref publishing, and install-truth process; do not manually bypass that
  release ownership.
- At close, record what shipped, what remains deferred and why, fresh roadmap
  candidates and triggers, and the next default action. Between feature
  milestones, prefer the sustaining GA release train over automatic expansion.
- Make the boundary concrete: fresh main SHA, complete local contributor gate,
  canonical required CI and matching Release push no-publish outcome, reviewed
  PR/delivery disposition, clean owned worktrees, and coherent planning state.
  Recheck after merge; a clean feature branch or historical green run is not
  accepted main. Reuse REPO-HYGIENE-CHECKLIST.md and its existing exact-SHA
  command; do not create a parallel gate or duplicate expensive runs.
- At every run boundary, leave owned work committed and temporary resources
  safely retired, or record an explicit incomplete handoff: owner/purpose,
  branch/base/head, dirty paths or preserved snapshot/hash, unique-commit
  disposition, checks/results, blocker and next exact action. Preserve unknown
  work and unmerged commits; do not force-reset, stash blindly or delete by age.
  Archival, integration into green main and package publication are distinct.

HOW TO USE THIS GUIDE

At each new-milestone decision, read this guide with PROJECT.md, STATE.md,
ROADMAP.md, REQUIREMENTS.md, MILESTONE-ARC.md, supported-surface docs, and the
release/development train records. Reconcile any disagreement against current
code and evidence. Update this guide's provisional horizons only when the
milestone close or new evidence warrants it; keep MILESTONE-ARC.md as the
concise live ranking and rationale for immediate candidates.
