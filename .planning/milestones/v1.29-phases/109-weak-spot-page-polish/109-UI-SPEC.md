# Phase 109 — UI Design Contract

> Visual and interaction contract for Phase 109. Generated by gsd-ui-researcher fallback, verified by gsd-ui-checker fallback.

Phase 109 raises the weaker admin support, operations, configure, and onboarding pages to the v1.29 journey and design-system standard. It must use the Phase 107 journey contract and Phase 108 component primitives as locked inputs, not restart the admin UI design.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | Phoenix function components in `Lockspire.Web.Components.AdminComponents`; no external UI registry |
| Icon library | none for Phase 109; operator actions keep visible text labels |
| Font | System sans via `--ls-font-sans`; mono via `--ls-font-mono` for IDs, timestamps, URLs, token family identifiers, delivery IDs, user codes, and redacted values |

### Implementation Boundary

- Preserve the embedded Phoenix LiveView admin surface and the host-owned operator-auth/layout/branding seam.
- Keep `Lockspire.Web.Admin.CSS` as the single embedded admin CSS source and keep classes under the `lockspire-admin-*` namespace.
- Use the shared Phase 108 primitives where applicable: `page_hero`, `metric_grid`, `task_card` or `attention_card`, `filter_bar`, `resource_item`, `copy_once_secret_panel`, `action_group`, `empty_notice`, and `long_value`.
- Do not add Tailwind, shadcn, a theming engine, a JS animation dependency, third-party component registries, inline layout styles, or unrelated protocol behavior.
- Do not expose client secrets, token plaintext, registration access token plaintext, user codes, or verifier material in list rows, logs, screenshots, docs, or operator copy.

---

## Page Priority Contract

Phase 109 must polish these surfaces first, in this order:

| Priority | Routes / Surfaces | Journey | Primary Job |
|----------|-------------------|---------|-------------|
| 1 | Tokens and token detail | Support | Investigate account, client, token, refresh-family, sender-constraint, expiration, and revocation state |
| 2 | Consents and consent detail | Support | Investigate remembered grants by account, client, scope, status, and safe revocation path |
| 3 | Logout deliveries | Operate | Triage waiting, retrying, failed, discarded, and completed logout propagation work |
| 4 | Device authorizations | Operate | Triage pending, approved, denied, expired, and completed device-code flow state |
| 5 | Interactions | Operate | Inspect active authorization interaction queue state and age without raw-table overload |
| 6 | DCR onboarding and IAT inventory/new | Configure | Connect policy, IAT inventory, self-registered clients, RAT rotation, and partner handoff |
| 7 | Keys and client-detail action grouping | Configure | Separate routine posture review from risky key, credential, endpoint, and lifecycle actions |

Strong v1.28/v1.29 baseline routes such as Overview, policy pages, and most of the client workspace should be touched only where they provide source patterns or where action grouping is explicitly in scope.

## Visual Hierarchy

Primary visual anchor: the page's journey label, operator job statement, and attention-worthy state summary. Every Phase 109 route must answer, above the dense list or detail body:

1. What am I investigating or operating?
2. Which account, client, status, or incident dimension is currently selected?
3. What state needs attention now?
4. What is the next safe action?
5. Where can I pivot if this page is not enough context?

| Surface | Focal Point | Secondary Priority | Avoid |
|---------|-------------|--------------------|-------|
| Support lists | Filtered investigation context plus result count | Account/client/status pivots and safe detail links | Raw table as first content, hidden filter meaning |
| Support detail | A single grant/token health decision | Related client, account/subject, token family, scopes, timestamps, audit/revocation context | Secret material, ambiguous "active" copy |
| Operations lists | Queue health by status and age | Retry/discard/completed counts, worker or delivery context, detail links | Forcing operators to decode only timestamps and hashes |
| Configure weak spots | Current posture and safe mutation entry points | Related policy, IAT, self-registered client, key, or client action context | Mixing routine edits with destructive/credential actions |
| Mobile views | Wrapped resource rows and stacked actions | Badges and long values that remain readable | Page-level horizontal scrolling or clipped identifiers |

Icon-only actions are not allowed. If an existing route uses compact affordances, Phase 109 must keep visible labels or provide an accessible text label with nearby visible context.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Tiny inline gaps, badge internals, compact metadata separators |
| sm | 8px | Compact control gaps, label-to-value spacing, status cluster gaps |
| md | 16px | Default row/card/list padding and filter control gaps |
| lg | 24px | Page section padding, detail section spacing, confirmation panels |
| xl | 32px | Major layout gaps and mobile stacked section separation |
| 2xl | 48px | Empty-state vertical padding and major route breaks |
| 3xl | 64px | Reserved for page-level rhythm only; use sparingly |

Exceptions: none.

Control sizing:

- Standard buttons, links styled as buttons, and inputs use a minimum 40px height.
- Mobile stacked action groups stretch controls to full container width.
- Dense metadata and badges may be visually smaller, but clickable controls must remain easy to target through their row or action container.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 600 | 1.2 |
| Body | 14px | 400 | 1.5 |
| Heading | 16px | 600 | 1.25 |
| Display | 24px | 600 | 1.2 |

Rules:

- Use exactly these four sizes and two weights for new Phase 109 admin UI markup.
- Letter spacing is `0` for normal copy. Existing uppercase labels may use `0.05em` only when already established by the admin design system.
- Mono text is reserved for identifiers, URLs, timestamps, token family IDs, delivery IDs, user codes, command hints, and redacted values.
- Long mono values must use the `long_value` primitive or equivalent `overflow-wrap:anywhere` class treatment.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f9fafb` | Admin shell background and quiet page surfaces |
| Secondary (30%) | `#ffffff` | Cards, hero panels, filter bars, confirmation panels, and primary content surfaces |
| Accent (10%) | `#2563eb` | Primary CTA background, current nav indicator, resource title links, focused controls, and the single most important route action |
| Destructive | `#991b1b` | Destructive action text, destructive badges, destructive confirmation copy, and revocation/retirement confirmation state |

Accent reserved for: primary CTA background, current nav indicator, resource title links, focused controls, selected filter/pivot affordance, and the single most important route action. Accent must not be used for all links, every badge, decorative panels, or routine secondary actions.

Semantic status colors are separate from accent:

| Status | Contract |
|--------|----------|
| Success | Healthy, active, completed, published, copied, current, or verified state |
| Warning | Waiting, retrying, expiring, retiring, pending too long, disabled policy pressure, or exception state |
| Danger | Failed, discarded, reuse detected, revoked, expired when incident-worthy, disabled-risk, or destructive confirmation state |
| Info | Neutral pending, upcoming, explanatory support guidance, or operational background state |

Status badges must include text labels; color alone is never the only state cue.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Review incident context |
| Empty state heading | No investigation results match these filters |
| Empty state body | Adjust the account, client, status, or date filters, or return to the overview to choose a different support or operations workflow. |
| Error state | Investigation context could not be loaded. Check the selected account, client, status, or identifier, then reload this support workflow. |
| Destructive confirmation | Revoke token family: confirm the affected client, subject, token family, and irreversibility before revoking every active token in the family. |

Copy rules:

- Use the locked journey labels exactly: Orient, Configure, Support, Operate.
- Use `DCR onboarding` for partner intake, IATs, self-registered clients, and RAT support. Use `DCR policy` only for issuer registration posture.
- Use `post-logout redirect URIs` for browser destinations and `logout propagation URIs` for RP cleanup endpoints.
- CTA labels must be verb plus noun: `Filter tokens`, `Review token`, `Revoke token family`, `Filter consent grants`, `Review stored grant`, `Review logout deliveries`, `Retry logout delivery`, `Review device authorizations`, `Review interactions`, `Mint initial access token`, `Review key lifecycle`, `Rotate client secret`.
- Do not add generic labels such as `Submit`, `OK`, `Cancel`, `Apply`, `Open`, or `Save` without a noun.
- Empty states must say what is absent and offer a next route, filter adjustment, or safe creation action.
- Error states must identify the failed context and a next fix path, not only that loading failed.
- Secret-bearing copy must say `copy once`, `redacted`, or `not shown again` where relevant and must not imply operators can recover plaintext later.

### Destructive And Risky Actions

| Action | Confirmation Contract |
|--------|-----------------------|
| Revoke consent grant | Name the client, subject/account, scopes if available, and state that the remembered grant will no longer authorize future consent reuse. |
| Revoke token | Name the token type, client, subject/account, expiration, and revocation reason. |
| Revoke token family | Name the token family, client, subject/account, active-token count if available, and family-wide irreversibility. |
| Retry logout delivery | Show endpoint/client/delivery ID and explain that retry re-enqueues delivery without changing logout event truth. |
| Discard logout delivery | Name endpoint/client/delivery ID and explain that delivery will no longer retry. |
| Retire or activate key | Name key ID, use, state, and signing/encryption consequence. |
| Rotate client secret or registration access token | Use copy-once panel wording and separate from routine client edits. |
| Revoke initial access token | Name token label/client/policy context if available and explain partner intake consequence. |

## Route-Specific Interaction Contracts

| Route / Surface | Required Pattern |
|-----------------|------------------|
| `/admin/tokens` | Use `filter_bar` for account/client/status/date criteria, `metric_grid` or summary strip for active/revoked/expired/reuse-detected counts, and `resource_item` rows with token type, client, subject/account, family, status, and last timestamp. |
| `/admin/tokens/:id` | Lead with token health decision and safe revocation actions. Show token family, sender-constraint, client, subject/account, issuance/expiry/revocation timestamps, and pivots to client/related family without exposing plaintext tokens. |
| `/admin/consents` | Use `filter_bar` for account/client/status/scope criteria and rows that expose client, subject/account, scopes, remembered/revoked state, and updated timestamp. |
| `/admin/consents/:id` | Lead with grant status and revocation decision. Show scopes, client, subject/account, creation/update/revocation context, and pivots to tokens/client where available. |
| `/admin/logouts` | Show delivery status buckets before rows. Rows must expose client, endpoint, status, attempt count, next retry or completed/discarded timestamp, and safe retry/discard actions. |
| `/admin/device_authorizations` | Show pending/approved/denied/expired/completed buckets and age. Rows must expose client, subject/account when present, user-code state as redacted or non-secret context, expiration, and next safe review action. |
| `/admin/interactions` | Show active interaction age, client, subject/account when known, prompt/status, expiration, and support pivots without making raw interaction IDs the main anchor. |
| `/admin/dcr` and `/admin/iats` | Keep DCR onboarding as one configure journey. Connect global DCR policy, IAT inventory, self-registered clients, RAT rotation, expiration, revocation, and partner handoff copy. |
| `/admin/iats/new` | Use a focused create form with policy reminder, scope/expiration/label context, copy-once result panel, and no raw secret persistence outside the result panel. |
| `/admin/keys` and `/admin/keys/:id` | Preserve strong key lifecycle patterns while improving long key IDs, state badges, safe action separation, and mobile wrapping. |
| `/admin/clients/:client_id` action areas | Group routine configuration, credential rotation, DCR/RAT, logout endpoints, PAR/security policy, and lifecycle/destructive actions into distinct `action_group` sections with danger actions visually separated. |

## Mobile And Responsive Contract

- At 390px width, Phase 109 target routes must not require page-level horizontal scrolling.
- Long client IDs, token family IDs, logout delivery IDs, interaction IDs, URLs, timestamps, subjects, and user-code-adjacent values must wrap inside their container.
- Filter bars collapse to one column below 720px and keep result-count/help text adjacent to the controls.
- Resource rows stack in this order on mobile: title, status cluster, subtitle/context, long values, metadata, actions.
- Action groups stack vertically on mobile and preserve primary, secondary, and destructive separation after wrapping.
- Tables may retain horizontal scrolling only as a compatibility fallback; the primary support/operations experience should use rows, cards, summaries, and filters that can be scanned without decoding raw tables.
- Text must not overlap badges, buttons, filters, long values, or adjacent rows.

---

## Motion And Interaction Contract

Motion is CSS-only and must serve feedback, focus/hover affordance, or state continuity.

| Token | Value | Usage |
|-------|-------|-------|
| `--ls-motion-duration-fast` | 150ms | Hover, focus, border, background, and shadow feedback |
| `--ls-motion-duration-medium` | 220ms | Reserved for small disclosure or flash continuity |
| `--ls-motion-ease-standard` | `cubic-bezier(0.4, 0, 0.2, 1)` | Default easing |

Rules:

- Respect `prefers-reduced-motion`; reduce transition/animation duration to near-zero and disable active transforms.
- Do not add decorative motion, route-transition choreography, or a broad LiveView JS animation layer.
- Focus states must remain visible on primary nav, secondary nav, filters, row links, buttons, confirmation controls, and copy-once panels.
- Disabled actions must explain why they are unavailable or route the operator to the missing prerequisite.

---

## Security And Redaction Contract

- Client secrets, registration access tokens, initial access token plaintext, refresh/access token plaintext, user codes, verifier material, and raw credentials must never appear in rows, screenshots, docs, logs, flash messages, or copied error text.
- Redacted values should use consistent text such as `Redacted after creation` or `Shown once after rotation`.
- Token, consent, logout, device, and interaction rows may show hashed IDs, database IDs, family IDs, client IDs, subject/account IDs, timestamps, status, and endpoint URLs only when already part of the admin domain contract.
- Confirmation panels for destructive support actions must show enough non-secret context for the operator to avoid acting on the wrong resource.
- Screenshot proof in Phase 110 must use demo seed values that exercise long-value wrapping without resembling real secrets.

---

## Contract Fences

Phase 109 planning should add or extend deterministic proof for:

- Support and operations routes using journey labels, page job copy, and verb-plus-noun action labels.
- No generic CTA labels in newly touched admin routes.
- No inline layout styles or arbitrary non-`lockspire-admin-*` admin classes.
- Use of shared primitives for filter bars, resource rows, long values, empty states, confirmation panels, and action groups on touched routes.
- Mobile no-overflow assertions or browser proof at 390px for tokens, consents, logout deliveries, device authorizations, interactions, IATs, keys, and client detail action groups.
- Redaction assertions that secret/token plaintext is absent from list/detail HTML, logs, docs, and screenshot seed fixtures.
- Destructive/risky actions have confirmation copy naming the affected resource and consequence.

Browser screenshots, route-wide click-through, final screenshot inventory, and docs regression proof remain Phase 110 scope unless a Phase 109 page cannot be trusted without a focused screenshot.
