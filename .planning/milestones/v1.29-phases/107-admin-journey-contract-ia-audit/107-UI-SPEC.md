# Phase 107 - UI Design Contract

> Visual and interaction contract for the admin journey contract and IA audit phase. Generated by gsd-ui-researcher fallback, verified by gsd-ui-checker fallback.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | Phoenix LiveView components in `Lockspire.Web.Components.AdminComponents` |
| Icon library | none in current admin surface; do not introduce icons in Phase 107 |
| Font | `--ls-font-sans` for UI copy and `--ls-font-mono` only for IDs, timestamps, URIs, commands, and secret material |

Phase 107 must preserve the existing `lockspire-admin-*` BEM/design-token architecture in `Lockspire.Web.Admin.CSS`. This phase produces route contracts, audit matrices, and acceptance rubrics; it must not introduce Tailwind, shadcn, a theming engine, a new JS animation dependency, or arbitrary one-off class naming.

---

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline metadata gaps, dense rubric cells |
| sm | 8px | Compact control gaps, badge groups, table cell internals |
| md | 16px | Default field, list, and card content spacing |
| lg | 24px | Card padding, route-section spacing, form group spacing |
| xl | 32px | Page body padding and major layout gaps |
| 2xl | 48px | Empty-state and audit-summary breathing room |
| 3xl | 64px | Page-level separation in documentation artifacts only |

Exceptions: none

Phase 107 audit outputs must record existing surfaces that depend on intermediate token values outside this contract, but the planner must not add new spacing values during this phase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 600 | 1.25 |
| Body | 14px | 400 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.15 |

Only the two declared weights are allowed in Phase 107 artifacts: 400 for explanatory text and 600 for labels, route names, headings, and key values. The audit may note existing heavier weights as baseline evidence, but new contract copy should not expand the type scale.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--ls-color-gray-50` / white | Page background, admin body, audit document background, neutral route rows |
| Secondary (30%) | `--ls-color-gray-100` / `--ls-color-gray-200` | Cards, table dividers, inactive navigation, rubric borders |
| Accent (10%) | `--ls-color-brand-600` | Primary CTA, active navigation item, focus-visible outline, route-owner highlight in audit matrices |
| Destructive | `--ls-color-danger-text` / `--ls-color-danger-bg` | Destructive actions only: revoke grant, revoke token, revoke refresh family, retire key, rotate client secret/RAT when shown as high-risk |

Accent reserved for: primary CTA, active navigation item, focus-visible outline, and the single selected route or journey row in audit views. Accent must not be used for all links, every badge, decorative panels, or status colors.

Status color meanings stay semantic:

| Status | Usage |
|--------|-------|
| Success | healthy, active, completed, current, verified |
| Warning | expiring, retiring, retryable, policy exception pressure |
| Danger | failed, discarded, reuse detected, revoked, destructive confirmation |
| Info | upcoming, pending, explanatory support guidance |

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Record route audit |
| Empty state heading | No route findings recorded yet |
| Empty state body | Start with the admin overview, then record the route's journey, operator job, primary decision, next action, empty state, risk state, and follow-up route. |
| Error state | Route audit is incomplete. Add one primary journey, one primary operator job, one primary action, and one follow-up route before planning implementation work. |
| Destructive confirmation | No new destructive action is introduced in Phase 107. Existing destructive actions must keep explicit confirmation panels that name the affected grant, token, token family, key, client secret, or registration access token and describe reversibility. |

Copy rules:

- Use the four top-level journey names exactly: Orient, Configure, Support, Operate.
- Every route must have one primary journey and one primary operator job, even when it supports secondary pivots.
- CTA labels must be verb plus noun: `Record route audit`, `Open client workspace`, `Review logout deliveries`, `Edit DCR policy`, `Mint initial access token`.
- Do not use generic labels such as `Submit`, `OK`, `Cancel`, `Apply`, or `Open workflow` in new Phase 107 recommendations.
- Use `DCR onboarding` for the partner intake journey and `DCR policy` for issuer registration posture.
- Use `post-logout redirect URIs` for browser destinations and `logout propagation URIs` for RP cleanup endpoints.
- Empty states must say what is absent and where the operator should go next.
- Error states must identify the missing contract field and the next fix, not only that validation failed.

## Visual Hierarchy Contract

Primary visual anchor: the route's journey and job statement. The top of every audited route must answer, in order:

1. What journey am I in?
2. What operator job does this page own?
3. What state needs attention?
4. What is the next safe action?
5. Where do I pivot if this is not the right workflow?

Focal points by journey:

| Journey | Focal point | Secondary content | Risk cue |
|---------|-------------|-------------------|----------|
| Orient | Provider attention summary and next-action routing | Journey cards and counts | Warning/danger counts only |
| Configure | Current posture, exceptions, and safe mutation entry points | Client/key/policy details | Destructive and credential actions separated from routine edits |
| Support | Account/client/status investigation context | Revocation history and pivots | Reuse detected, revoked, expired, disabled |
| Operate | Queue state, delivery status, retry/discard pressure | Timestamps and protocol identifiers | Retryable, failed, discarded, expired |

No route may rely on raw table density as the first visual anchor. Dense lists and tables must be supported by route heading copy, summary metrics, filters, or resource rows that expose the operator decision first.

## Mobile And Responsive Contract

Phase 107 must audit, not implement, the following mobile acceptance rules:

- No route in the approved admin surface may require page-level horizontal scrolling at 390px width.
- Long client IDs, URLs, token family identifiers, timestamps, command hints, and logout URIs must wrap within their container.
- Navigation may scroll horizontally, but content rows, cards, action groups, and confirmation panels must stack predictably.
- Client detail, tokens, consents, interactions, device authorizations, logout deliveries, DCR, IAT, keys, and policy routes must be explicitly classified as strong, adequate, or weak on mobile.
- Action groups must keep primary, secondary, and destructive actions visually distinct after wrapping.

---

## Motion And Interaction Contract

Motion is allowed only for orientation, feedback, and state continuity. Existing transitions on buttons, links, focus, and cards must remain subtle and must respect `prefers-reduced-motion`.

Phase 107 audit outputs must record whether each route has:

- keyboard-visible focus on primary navigation, secondary navigation, buttons, links, and destructive confirmations
- disabled state copy where an action is unavailable
- confirmation-backed risky actions
- copy-once treatment for client secrets and registration access tokens
- clear hover/active states without changing layout dimensions

No new animation pattern is approved in Phase 107.
