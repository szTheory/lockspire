## Overview purpose follow-up — 2026-10-12

- User feedback: Overview should help authorized engineers and support staff choose an investigation or management task, rather than mix policy configuration, historical problems, pending user steps and inventory into a generic activity card. A tooltip does not make unrelated information relevant to Overview.
- Replaced “Needs review” and “Current activity” with four purpose-specific sections: **Security events**, **Sign-out problems**, **Waiting for users**, and **Apps and access**. Counts link to their corresponding records. Reuse and delivery totals include retained records; they are not counts of unresolved incidents or users still signed in. No acknowledgement, resolution or new queue operation is invented.
- Reuse explanations identify possible theft or a repeated app request without asserting compromise, retain the automatic family-wide revocation consequence, and point to investigation. Primary reference: [OAuth security BCP, refresh-token protection](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2). Delivery failure means sign-out may be unconfirmed, not proven session persistence or proven compromise.
- Removed the security-policy mini-table and app-setup-token count/read from Overview. Their existing Security and App registration destinations remain accessible through navigation. Detailed PAR/DPoP/security profile/token format choices belong beside their configuration and explanation, rather than behind Overview labels such as “Request step” or an invented security-level ranking.
- Kept an active token-signing-key count under Apps and access, with an explanation of signature verification and a link to Keys. Only active `:sig` keys count; active encryption keys do not. Upcoming/retiring details remain on the existing key-management page. The count is inventory, not a token-issuance health test.
- Pending interaction/device totals and linked pending views now exclude expired requests using the same status and future-expiry predicate. Full inventories preserve their historical records. A remaining older full-history copy issue is recorded for the queue pass: a stored expired-but-pending row still uses its recorded pending wording; this follow-up does not claim that all lifecycle presentation on those routes has been normalized.
- Retained existing branding/components/tokens and used a scoped two-column Overview layout with one column at narrow widths. Counts remain aligned beside their labels on mobile. Two isolated reviewers checked semantics and layout; the bare Registered apps row styling was corrected before browser confirmation.
- Added the canonical Lockspire SVG favicon to the adoption demo’s **admin root layout only**, served through its existing `/lockspire-assets` mount. The host continues to own its document head; no global favicon injection or host-page override was added. The served asset matches `brandbook/logo/lockspire-favicon.svg` byte-for-byte, and demo smoke checks its link, successful delivery and SVG MIME type.
