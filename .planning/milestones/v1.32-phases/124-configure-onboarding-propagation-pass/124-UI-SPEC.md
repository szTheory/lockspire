# Phase 124 - UI Design Contract

> Visual and interaction contract for Phase 124: Configure Onboarding Propagation Pass. Generated by gsd-ui-researcher for planner, executor, checker, and auditor use.

Phase 124 propagates the strongest v1.32 page patterns into existing Configure flows: clients, DCR onboarding, initial access tokens, keys, and policy pages. This phase must not broaden public APIs, add admin routes, rebuild the admin shell, add public lab/browser-proof routes, change storage schemas, change OAuth/OIDC protocol behavior, introduce public theming, or move host-owned authentication, tenant policy, layout, branding, or developer portal UX into Lockspire.

Sources: `AGENTS.md`, `.planning/STATE.md`, `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`, `124-CONTEXT.md`, `121-ROUTE-SCORECARDS.md`, `122-UI-SPEC.md`, `123-UI-SPEC.md`, `brandbook/`, `lib/lockspire/web/admin_css.ex`, `lib/lockspire/web/components/admin_components.ex`, current Configure LiveViews/tests, and `npx shadcn info` on 2026-06-29.

## Design System

| Property | Value |
|----------|-------|
| Tool | none; Phoenix function components plus embedded `lockspire-admin-*` CSS |
| Preset | not applicable |
| Component library | Lockspire-owned `Lockspire.Web.Components.AdminComponents` and existing LiveView/AdminLayout surfaces |
| Icon library | none; use visible text labels for Configure actions, status meaning, handoff states, and route pivots |
| Font | `--ls-font-display` Familjen Grotesk stack for headings; `--ls-font-sans` Inter stack for UI/body; `--ls-font-mono` JetBrains Mono stack for IDs, handles, timestamps, URLs, credential placeholders, and redacted values |
| CSS architecture | BEM/design-token `lockspire-admin-*`; no Tailwind migration, shadcn adoption, public theming engine, host registry, data-grid package, or arbitrary one-off classes |

Implementation boundary:

- Use existing Configure routes only: `/admin/clients`, `/admin/clients/:client_id`, client edit/query workflows, `/admin/dcr`, `/admin/iats`, `/admin/iats/new`, `/admin/keys`, `/admin/keys/:id`, `/admin/policies`, `/admin/policies/par`, `/admin/policies/security-profile`, `/admin/policies/dpop`, and `/admin/policies/dcr`.
- Preserve the Phase 121 route truth: `Lockspire.Web.AdminRouter` plus exactly `/admin/clients/:client_id/edit?workflow=logout-propagation` as a query workflow, not a new route.
- Use existing primitives by default: `page_hero`, `decision_summary`, `entity_header`, `pane`, `workflow_shell`, `section_card`, `metric_grid`, `resource_list`, `resource_item`, `dense_resource_row`, `lifecycle_row`, `status_badge`, `long_value`, `form_field`, `error_summary`, `error_list`, `empty_state`, `copy_once_secret_panel`, `action_group`, `action_bar`, `admin_button`, `confirmation_panel`, and `policy_nav`.
- Promote Support/Operate-proven patterns only. Do not add a new Configure meta-component unless duplication across touched pages becomes error-prone and the component remains internal, route-specific, and covered by source contracts.
- Keep LiveViews responsible for URL filters, forms, event handling, validation, copy-once reveal state, and Admin API results. Components render hierarchy, state treatment, wrapping, and confirmation structure.
- Do not add public component APIs, a Storybook/lab route, a host theming registry, a developer portal, external UI packages, or new admin shell navigation.

## Configure Route Contract

| Route | Primary Job | Primary Decision | Primary Action | Required Follow-Up |
|-------|-------------|------------------|----------------|--------------------|
| `/admin/clients` | Find or create a client and reach the right workspace. | Which client needs setup, review, or support? | `Filter clients` and `Create client` | Link rows to `/admin/clients/:client_id`; copy-once client-secret result stays on creation only. |
| `/admin/clients/:client_id` | Inspect one client's identity, posture, credentials, endpoints, DCR/RAT context, support pivots, and lifecycle state. | Is this client healthy, risky, or ready for a specific mutation? | `Review client configuration` | Route to focused edit, endpoint, policy, credential, DCR, Support, and Operate pivots only when backed today. |
| `/admin/clients/:client_id/edit` | Edit routine client metadata and basic configuration. | Which safe metadata should change? | `Save metadata` | Return to `/admin/clients/:client_id`. |
| `/admin/clients/:client_id/redirects` | Maintain exact-match browser callback destinations. | Are redirect URIs exact, current, and intentionally allowed? | `Save redirect URIs` | Return to client detail. |
| `/admin/clients/:client_id/logout-uris` | Maintain post-logout browser destinations. | Which browser destinations may receive the user after logout? | `Save post-logout redirect URIs` | Point to logout propagation workflow when cleanup endpoints are needed. |
| `/admin/clients/:client_id/edit?workflow=logout-propagation` | Maintain RP cleanup endpoints separately from browser redirects. | Which back-channel/front-channel cleanup endpoints receive logout propagation? | `Save logout propagation` | Safe context pivot to `/admin/logouts`; no retry/discard/worker controls. |
| `/admin/clients/:client_id/par-policy` | Set client-specific PAR override and show effective posture. | Should this client inherit or override issuer PAR posture? | `Save PAR policy` | Safe context pivot to `/admin/policies/par`. |
| `/admin/clients/:client_id/security-profile` | Set client-specific security profile and show readiness impact. | Should this client inherit, opt in, or opt out of stricter security? | `Save security profile` | Safe context pivot to `/admin/policies/security-profile`. |
| `/admin/clients/:client_id/rotate-secret` | Rotate confidential client credential with copy-once reveal. | Is this credential rotation intentional and ready for handoff? | `Rotate client secret` | Copy once, acknowledge, then return to redacted client posture. |
| `/admin/clients/:client_id/rotate-registration-access-token` | Rotate DCR Registration Access Token with copy-once reveal. | Is RAT rotation intentional and ready for partner handoff? | `Rotate registration access token` | Copy once, acknowledge, then return to redacted DCR/RAT posture. |
| `/admin/dcr` | Guide partner onboarding from policy to IATs to self-registered clients. | What is the next DCR onboarding step? | `Mint initial access token` | Link to `/admin/iats/new`, `/admin/iats`, `/admin/policies/dcr`, and self-registered client detail. |
| `/admin/iats` | Review DCR intake-token inventory. | Which intake tokens are active, used, expired, or revoked? | `Review initial access tokens` | Link to `/admin/iats/new`; active revoke must use inline confirmation if touched. |
| `/admin/iats/new` | Create a bounded DCR intake token and handle plaintext safely. | What intake-token constraints should be issued? | `Mint initial access token` | Copy once, acknowledge, then return to `/admin/iats` redacted inventory. |
| `/admin/keys` | Review issuer key posture and rollover readiness. | Are active, upcoming, retiring, and retired keys ready for JWKS exposure? | `Review key lifecycle` | Link each key to `/admin/keys/:id`; generation actions stay explicit and backed by existing Admin APIs. |
| `/admin/keys/:id` | Inspect one key's public metadata and lifecycle transitions. | What lifecycle transition is safe for this key? | `Review key lifecycle` | Return to `/admin/keys` after publish, activate, or retire consequence. |
| `/admin/policies` | Choose which issuer-level policy needs review first. | Which global policy needs attention? | Route-specific review links, not generic `Open workflow` | Link to PAR, security profile, DPoP, or DCR policy route. |
| `/admin/policies/par` | Decide global PAR posture. | Should PAR be optional or required by default? | `Save global PAR policy` | Link to client PAR override context. |
| `/admin/policies/security-profile` | Decide global security profile posture. | Which issuer security profile should apply by default? | `Save global security profile` | Link to client security override context. |
| `/admin/policies/dpop` | Decide global DPoP sender-constraint posture. | Should DPoP be required, optional, or disabled by default? | `Save global DPoP policy` | Link back to policy overview and client exceptions. |
| `/admin/policies/dcr` | Gate partner self-registration and allowed DCR metadata. | Which DCR policy safely gates partner registration? | `Save global DCR policy` | Link to `/admin/dcr`; do not mint IATs on this route. |

Every Configure page must answer, in this order:

1. Which Configure workflow am I in?
2. What is the current posture or inventory state?
3. What is the next safe action?
4. Which support, policy, or adjacent Configure route explains the state?
5. What risky action consequence applies, if any?

- Destructive action groups keep the existing left divider on desktop and top divider below 720px.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--ls-surface-page`: light `#f8fafc`, dark `#0b1220` | Admin shell background and broad quiet page surface |
| Secondary (30%) | `--ls-surface-panel`: light `#ffffff`, dark `#131c2e`; plus `--ls-surface-muted` | Page heroes, panes, section cards, workflow shells, rows, policy summaries, empty states, copy-once panels, confirmation panels |
| Accent (10%) | `--ls-text-accent`: light Deep Cyan `#0e7490`, dark Signal Cyan `#22d3ee` | Configure eyebrow, active/current navigation, primary safe CTAs, selected route context, resource title links, and focus-visible rings only |
| Destructive | `--ls-status-danger-*`: light text `#991b1b` / bg `#fee2e2`; dark text `#fca5a5` / bg `#2e1517` | Disable client, rotate credential, revoke IAT, retire key, destructive confirmation panels, validation/error states, and incident posture only |

Accent reserved for: `Configure` eyebrow, active/current navigation, primary safe CTAs, selected policy/onboarding context emphasis, resource title links, and focus-visible rings. Accent must not be used for decorative panels, every badge, every link indiscriminately, all metadata labels, or normal body text.

Status semantics:

| Status Group | Contract |
|--------------|----------|
| Success / healthy | Active clients, IAT-gated registration, active/usable intake tokens, publishable key overlap, saved policy state. |
| Warning / waiting | Open registration risk, upcoming key before cutover, expiring intake token, mixed-mode security override, best-effort front-channel logout posture. |
| Danger | Disabled client when consequence is blocking, revoke/retire/rotate confirmations, unsafe broad registration posture, failed validation, impossible lifecycle transition. |
| Disabled / closed | Disabled clients, revoked/expired/used IATs, retired keys, unavailable actions, no override/inherit states when no action is needed. |
| Completed | Created client, minted IAT after acknowledgement, key transition complete, policy save success, copy-once handoff acknowledged. |
| Provenance / info | Operator-created versus self-registered client, DCR/RAT context, policy inheritance, public key metadata, support route pivots. |

Color is never the only state signal. Badges must include visible text, decision summaries must include details, confirmation copy must name consequences, and errors must describe the next safe path without backend leakage.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Mint initial access token` for DCR onboarding; route-specific CTAs elsewhere: `Filter clients`, `Create client`, `Review client configuration`, `Save metadata`, `Save redirect URIs`, `Save post-logout redirect URIs`, `Save logout propagation`, `Save PAR policy`, `Save security profile`, `Save global DCR policy`, `Generate signing key`, `Generate encryption key`, `Review key lifecycle`. |
| Empty state heading | Clients: `No clients match this view`; DCR: `No self-registered clients yet`; IATs: `No initial access tokens minted`; IAT draft: `No intake token minted yet`; keys: `No signing keys are stored`; key detail: `Signing key not found`; client detail: `Client not found`; policies: `No policy exceptions visible`. |
| Empty state body | Clients: `Adjust the search, status, or provenance filters, or create a client using the registration form.` DCR: `Mint an initial access token or edit DCR policy before partner self-registration starts.` IATs: `Mint a short-lived intake token to allow a partner to dynamically register a client.` Keys: `Generate signing or encryption key material before relying on JWKS publication.` Policies: `Open the detailed policy route that owns the issuer setting you need to review.` |
| Error state | `Configure context could not be loaded. Reload this workflow or return to the previous Configure route; no unsupported action was taken.` Field errors must attach to fields and preserve entered values. Mutation errors must name what did not change. |
| Destructive confirmation | `Disable client`: confirm future OAuth/OIDC requests for this client are blocked until re-enabled. `Rotate client secret`: confirm the previous secret stops being current and plaintext is revealed once. `Rotate registration access token`: confirm the previous RAT stops being current and plaintext is revealed once. `Revoke initial access token`: confirm partners using this intake token can no longer dynamically register clients with it. `Retire key`: confirm the public key leaves publication overlap after verifiers have moved off it. |

Copy rules:

- Use the journey label `Configure` exactly.
- Use verb-plus-noun labels. Approved labels include `Filter clients`, `Create client`, `Review client configuration`, `Edit client metadata`, `Save metadata`, `Save redirect URIs`, `Save post-logout redirect URIs`, `Save logout propagation`, `Edit PAR policy`, `Save PAR policy`, `Edit security profile`, `Save security profile`, `Rotate client secret`, `Rotate registration access token`, `Review DCR onboarding`, `Mint initial access token`, `Review initial access tokens`, `Save global PAR policy`, `Save global security profile`, `Save global DPoP policy`, `Save global DCR policy`, `Generate signing key`, `Generate encryption key`, `Publish key`, `Activate key`, and `Retire key`.
- Replace generic Configure CTAs in touched surfaces. Do not introduce `Submit`, `Apply`, `OK`, `Open workflow`, `Go`, `Continue`, one-word `Manage`, one-word `Revoke`, or one-word `Save`.
- Copy-once copy must say plaintext is shown once, Lockspire stores only the hash or redacted durable state, and the operator must copy before acknowledging.
- Confirmation copy must name the concrete consequence and closed state. It must not imply plaintext recovery, export, reveal-again, developer-portal delivery, host account mutation, worker control, or policy effects outside the existing Admin API behavior.
- Error copy must avoid backend leakage and secret values. It must say what context failed and what the operator should do next.

## Page Composition Contract

### Shared Configure Spine

- Lead touched Configure detail, onboarding, inventory, key, and policy pages with `page_hero` using eyebrow `Configure`, route-specific title, and one sentence naming the operator job.
- Put current posture or selected context before dense lists or forms. Use `decision_summary` when the operator must understand posture plus next safe action; use `metric_grid` and dense rows when scanability is the primary task.
- Group actions with `action_group` when primary, secondary, and destructive controls coexist. Use `action_bar` only for simple form-local or pane-local action rows.
- Use `confirmation_panel` for risky or destructive Configure actions whenever the action needs confirmation and the page has room for inline consequence copy.
- Use `copy_once_secret_panel` for client secret, initial access token, and RAT plaintext. After acknowledgement, pages must return to redacted durable posture or inventory.
- Use `long_value` for all long IDs, URLs, timestamps, handles, and redacted placeholders. Do not manually truncate sensitive-looking values.

### Clients

- `/admin/clients` must make filtering and client selection the first task. If touched, add or preserve a `page_hero` or top section that names `Client inventory`, selected filters, total matching clients, and the create path.
- Client inventory primary filter action is `Filter clients`, not `Apply`. Row title links open client detail; row metadata shows status, provenance, and enough posture to select the right client without duplicating detail-page sections.
- Client creation stays inside the existing Admin API path. The created-client result must show `copy_once_secret_panel` only when plaintext exists, otherwise a redacted/public-client explanation.
- `/admin/clients/:client_id` uses the current rich workspace as the reference Configure pattern: `page_hero`, `entity_header`, posture panes before mutation panes, grouped safe/secondary/destructive actions, support pivots, DCR/RAT context, and lifecycle confirmation.
- Client edit workflows must remain focused: routine metadata, redirect URIs, post-logout redirect URIs, logout propagation URIs, PAR override, and security profile override each keep their own title, help, fields, validation, and save copy.
- Client lifecycle enable/disable must use `confirmation_panel` with checkbox confirmation, non-secret client identifier, consequence copy, and accessible error output.

### DCR And IAT

- `/admin/dcr` must read as an onboarding hub, not a policy form clone. The hierarchy is: DCR policy posture, intake-token state, self-registered client results, then RAT/support handoff.
- Use a `decision_summary` on DCR onboarding when it improves step clarity. Required items when present: `Registration gate`, `Intake tokens`, `Self-registered clients`, and `Next safe action`.
- DCR onboarding primary action is `Mint initial access token`; secondary actions are `Review initial access tokens` and `Edit DCR policy`.
- Self-registered clients render as resource rows or resource items with status and safe client-detail links. Do not expose RAT plaintext, client secrets, or developer-portal affordances.
- `/admin/iats` must expose intake state before row metadata: active, used, expired, revoked, and total. Active revoke must move from browser `data-confirm` to inline `confirmation_panel` if this surface is touched.
- IAT rows must show redacted IAT handle, creator, expiry, last state change, usage/limit, and visible status. Plaintext never appears in inventory.
- `/admin/iats/new` must show constraints before minting and `copy_once_secret_panel` after minting. The acknowledgement label remains explicit, for example `I have copied this secret`.

### Keys

- `/admin/keys` must keep key inventory about lifecycle readiness, not raw crypto curiosity. Metrics show active, upcoming, retiring, retired, and total keys before rows.
- Key generation controls are existing backed actions and may remain, but they must be visually grouped as safe key-creation actions and use `Generate signing key` / `Generate encryption key`.
- Key rows must show key handle, use, publication/activation timestamps, JWKS visibility, status badge, and next action summary. Never show private JWK material.
- `/admin/keys/:id` must show public metadata, lifecycle state, and one safe next action. Publish, activate, and retire remain separate confirmation panels; retire uses destructive styling.
- Key lifecycle notices must distinguish `just changed`, `already in state`, and `could not change`.

### Policies

- Policy overview uses `policy_nav` and route-specific policy cards. If touched, replace `Open workflow` with `Review PAR policy`, `Review security profile`, `Review DPoP policy`, and `Review DCR policy`.
- Global policy pages must summarize current posture before the form. Use `decision_summary` for DCR and security-profile posture; add it to PAR/DPoP only when it reduces ambiguity without creating a new component layer.
- `/admin/policies/dcr` already carries the strongest policy summary pattern. Preserve its four-part summary: `Registration gate`, `Metadata allowlists`, `Token auth methods`, and `Default lifetimes`.
- Global policy save forms must state their scope: future issuer policy, clients that inherit, or future DCR requests only. They must not imply client-specific mutation unless a client route performs it.
- Policy forms must not mint IATs, rotate RATs, create credentials, mutate clients, fetch remote keys, reset nonces, debug tokens, or change host-owned tenant policy.

## Interaction Contract

| Interaction | Required Behavior |
|-------------|-------------------|
| Configure navigation | Existing navigation and policy nav stay stable. Do not add routes or shell groups. |
| Safe route pivot | Allowed only to existing routes. Link copy must name the destination job and must not read like a command against the current resource. |
| Filters | URL-owned where already URL-owned; selected context remains visible above results. Submit label must name the filtered resource. |
| Forms | `form_field` labels and help attach to controls. Validation preserves input and renders field or summary errors without backend detail. |
| Copy-once handoff | Plaintext appears only immediately after create/rotate/mint. Acknowledge clears plaintext and returns to redacted posture/inventory. No reveal-again, export, copy history, or recovery UI. |
| Confirmation | Use checkbox-confirmation forms inside `confirmation_panel` for risky/destructive actions. Missing confirmation renders visible errors and no mutation. |
| Status badges | Use `status_badge` with visible text plus surrounding consequence copy. Add status metadata only if fallback copy would mislead. |
| Long values | Use `long_value` with `kind: :id`, `:url`, `:timestamp`, `:token`, or `:text`. Never manually truncate secret-looking values. |
| Motion | Existing hover/focus transitions may remain. Do not add auto-refresh animation, motion-only status feedback, parallax, bounce, or progress animation. Reduced motion must neutralize nonessential transitions through current CSS. |
| Keyboard focus | Focus rings remain visible on nav links, policy nav, filters, fields, row links, checkbox confirmations, copy acknowledgement, save buttons, lifecycle buttons, and safe route pivots. |

Unsupported controls are explicitly banned unless already backed by an existing Admin API and named in this spec: reveal secret, reveal IAT, recover token, export credential, bulk revoke, bulk client lifecycle, force-publish, private-key export, retry/logout delivery, discard queue item, approve DCR request, deny DCR request, reset nonce, fetch remote JWKS, developer portal, host tenant policy editor, and public theming controls.

## State Coverage Contract

| State | Required UI Treatment |
|-------|-----------------------|
| Empty true-zero | Route-specific heading and body from the copy contract; show only safe create/review route pivots. |
| No-match filters | Preserve selected filters, show total matching count when available, and point to filter adjustment or client creation. |
| Dense inventory | Summary or metrics first, then resource rows. Keep title, status, posture, and next route visible before lesser metadata. |
| Copy-once active | Copy panel appears before any secondary metadata, uses mono wrapping, and includes explicit acknowledgement. |
| Copy-once acknowledged | Plaintext disappears; durable state is redacted and row/posture copy explains that recovery is unavailable. |
| Active/open | Success or healthy badge plus current safe action or route pivot. |
| Open registration warning | Warning posture with copy that says unauthenticated registration is broad and should have narrow allowlists/lifetimes. |
| Disabled/revoked/expired/used | Closed or disabled status with copy explaining no current intake/client action remains unless a backed route reopens it. |
| Lifecycle transition unavailable | Disabled/de-emphasized action or no-action copy that states why no action is available. |
| Validation/error | Specific error copy, no backend leakage, no secret values, accessible error list/summary, and unchanged state truth. |
| Long identifiers and URLs | `long_value` wrapping with no page-level horizontal overflow at 320px, 390px, 768px, 1024px, or 1440px. |
| Theme modes | Light, dark, and system modes use semantic `--ls-*` aliases; never hard-code new route colors. |
| Reduced motion | State and confirmation comprehension does not depend on animation. |

## Responsive And Accessibility Contract

- At 320px, 390px, 768px, 1024px, and 1440px, touched Configure pages must not require page-level horizontal scrolling.
- Below 720px, Configure rows stack in this order: title/decision, status cluster, posture/consequence copy, long values, secondary metadata, actions.
- Below 720px, form pages stack in this order: page/workflow heading, decision summary or help, field errors, fields, consequence copy, then actions.
- Copy-once panels must keep the value readable and wrapping; acknowledgement stays below the value and is reachable by keyboard.
- Confirmation panels stack after state summaries on mobile. Destructive actions must not visually precede state/consequence copy.
- Status meaning never relies on color alone; badge text and consequence copy are required.
- Focus rings use `--ls-focus-ring-*` tokens and must not be removed.
- `aria-describedby`, `aria-labelledby`, `aria-controls`, and label `for` targets must resolve when introduced.
- Error summaries use `role="alert"` where the existing component supports it; field errors must be adjacent to the affected control or linked by description.
- No icon-only actions, tooltip-only explanations, hover-only disclosures, or hidden support notes are approved.

## Security And Redaction Contract

- Never render client secret plaintext except during create/rotation copy-once state. Never render IAT plaintext except during mint copy-once state. Never render RAT plaintext except during RAT rotation copy-once state.
- Never render access token plaintext, refresh token plaintext, authorization codes, verifier material, cookies, session tokens, DPoP proofs, nonces, private keys, private JWK members, endpoint secrets, raw request objects, raw params, raw responses, Oban internals, SQL internals, or production-looking tenant URLs in UI, fixtures, flashes, docs, screenshots, logs, or tests.
- Continue using redacted handles for client, account/subject, IAT, token, consent, and durable support pivots where helpers exist.
- Configure pages may show durable non-secret metadata only: redacted handles, statuses, policy values, public key metadata, redirect/logout URLs, timestamps, counts, algorithm names, auth method names, and existing Admin API display names.
- Do not create copy-to-clipboard, reveal, decode JWT, inspect hash, export, bulk action, retry/discard, approve/deny, remote key fetch, nonce reset, raw audit dump, or developer portal controls.
- Screenshot/manual proof must use redaction-safe demo values that stress long wrapping without resembling real tokens, secrets, production tenants, or customer domains.
