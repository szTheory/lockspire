# v1.36 Structural Quality Ratchet — Independent Review

## Scope and evidence

Reviewed the implementation range `4fb1d41..536eb1c`, concentrating on executable
changes in the trusted-release path, CI matrix, adapter/port migration, token-endpoint
split, and the replacement test contracts. I traced the release workflow-run handoff,
the `TokenExchange` facade to grant coordinators and shared support, and repository

The token facade preserves its public result structs and its grant routing; the storage
changes consistently route host-repository access through the adapter. No protocol

automation, release evidence, CI static checks, the test-matrix writer, and token

also passed. All previously reported findings are resolved.

## Resolved findings

### RESOLVED BL-01: Release Please auto-merge CI/PR race

`release.yml` now dispatches the auto-merge workflow after the repo-owned Release Please
action has completed when it can find a successful canonical CI run for its exact source
SHA. The original `workflow_run` trigger remains for the opposite ordering. The
auto-merge workflow validates the supplied run through the GitHub API before any merge:
canonical workflow path, canonical workflow ID, repository, event, branch, SHA, status,
and conclusion all must match. Its zero-candidate branch is now a deliberate no-op rather
than a failed assertion. This closes the stranded-PR timing path while retaining
post-merge exact-SHA CI evidence before the release dispatch.

### RESOLVED WR-01: Failed test partitions omit timing JSON

`scripts/ci/run_test_matrix.sh` now records a non-zero partition in `overall_status`,
returns success from each partition wrapper, serializes JSON and the job summary, and only
then exits with the accumulated failure status. CI artifact upload under `always()` can
therefore retrieve failure evidence as intended.

### RESOLVED WR-02: GitHub release precedes Hex publication

The verified package is now published before the public GitHub release/tag is created.
This prevents release consumers from observing a tag for a version whose Hex publish
failed.

### RESOLVED WR-03: Post-Hex GitHub-release failure cannot be retried through the same workflow

`scripts/publish/publish_hex_idempotently.sh` is now the only package-publish path. It
requires the locally built tarball, calculates its SHA-256 checksum, and looks up the
exact package version from Hex. A 404 publishes the package normally. For an existing
release, it requires Hex's checksum to match the locally verified artifact before
continuing; it then publishes documentation only if Hex reports docs missing. Unexpected
HTTP statuses, failed transport, malformed/missing release data, or checksum mismatch all
fail closed. Thus a retry after a successful package publish can reach GitHub release
creation without accepting a mismatched pre-existing package, while the missing-docs
recovery branch remains explicit.

## Positive checks

- The token endpoint extraction retains the stable `Lockspire.Protocol.TokenExchange`
  facade and routes authorization-code, device-code, and CIBA exchanges through distinct
  coordinators while retaining shared validation and issuance support.
- Protocol key retrieval defaults now point to the Lockspire repository adapter rather
  than leaking a host Ecto repo into protocol modules; the adapter owns the configured
  host-repository interaction.
- Private-JWK decoding is centralized in a safe term/JSON decoder and preserves failure
  normalization to `:invalid_signing_key`.
- Immutable action pins, dependency lock checks, PostgreSQL digest pins, canonical CI
  path/workflow-ID checks, and exact post-merge SHA/CI validation materially strengthen
  the release surface.
- The duplicate `GrantSupport` grant router was removed; grant orchestration now has one
  public facade and dedicated grant coordinators, with the focused token test still
  passing.
- The idempotent publisher's expected Hex response shape was checked against a live Hex
  release: its `checksum` is a 64-character SHA-256 hex value and `has_docs` is present.

**Clean.** No remaining blocker or warning was proven in the reviewed v1.36 range.
