## Resolved findings

### RESOLVED BL-01: Release Please auto-merge CI/PR race

`release.yml` now dispatches the auto-merge workflow after the repo-owned Release Please
action has completed when it can find a successful canonical CI run for its exact source
SHA. The original `workflow_run` trigger remains for the opposite ordering. The
auto-merge workflow validates the supplied run through the GitHub API before any merge:
canonical workflow path, canonical workflow ID, repository, event, branch, SHA, status,
and conclusion all must match. Its zero-candidate branch is now a deliberate no-op rather
than a failed assertion. This closes the stranded-PR timing path while retaining
post-merge exact-SHA CI evidence before the release dispatch.

### RESOLVED WR-01: Failed test partitions omit timing JSON

`scripts/ci/run_test_matrix.sh` now records a non-zero partition in `overall_status`,
returns success from each partition wrapper, serializes JSON and the job summary, and only
then exits with the accumulated failure status. CI artifact upload under `always()` can
therefore retrieve failure evidence as intended.

### RESOLVED WR-02: GitHub release precedes Hex publication

The verified package is now published before the public GitHub release/tag is created.
This prevents release consumers from observing a tag for a version whose Hex publish
failed.

## Warnings

### WR-01: Post-Hex GitHub-release failure cannot be retried through the same workflow

**File:** `.github/workflows/release.yml:149-167`

**Issue:** Reordering publication fixes the false-public-release problem, but introduces
the inverse recovery hole: if `mix hex.publish --yes` succeeds and the following GitHub
release creation fails transiently, re-running the release workflow executes
`mix hex.publish --yes` again first. Hex rejects the existing version, so the retry never
reaches the GitHub release/tag creation step. The package is correctly public, but the
canonical tag/release may remain absent until manually repaired.

**Fix:** Make the package step idempotent. Before publishing, query Hex for the expected
version; publish only when absent, and fail if an existing version's package metadata is
not the intended release. With that guard, a rerun after Hex success can safely continue
to create or verify the matching GitHub release.

## Positive checks

  facade and routes authorization-code, device-code, and CIBA exchanges through distinct

  public facade and dedicated grant coordinators, with the focused token test still
  passing.
