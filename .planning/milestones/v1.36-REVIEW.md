# v1.36 Structural Quality Ratchet — Independent Review

## Scope and evidence

Reviewed the implementation range `4fb1d41..6a3fd36`, concentrating on executable
changes in the trusted-release path, CI matrix, adapter/port migration, token-endpoint
split, and the replacement test contracts. I traced the release workflow-run handoff,
the `TokenExchange` facade to grant coordinators and shared support, and repository
adapter calls through `Lockspire.Storage.Ecto.Repository`.

The token facade preserves its public result structs and its grant routing; the storage
changes consistently route host-repository access through the adapter. No protocol
security-default regression was proven in those paths. The release automation has one
ship-blocking liveness failure, however.

## Blockers

### BL-01: Release Please auto-merge can race the initial main CI and then never retry

**File:** `.github/workflows/release-please-automerge.yml:37-53`

**Issue:** The workflow is triggered only when a `CI` run completes. A normal main push
starts both `CI` and the `release.yml` Release Please job. If CI finishes before Release
Please has created its PR, lines 37-50 find zero open candidates; lines 51-53 then require
that the same main SHA already be the merge commit of a release PR and fail. Creation of
the PR does not itself create another main CI run, so there is no later workflow-run event
to merge it. The exact-post-merge evidence path is correct once a merge happens, but the
first required transition is timing-dependent and can leave every release PR stranded.

**Fix:** Make the zero-candidate case a successful no-op unless the current CI SHA is
known to be a release-PR merge, and add a deterministic second trigger/poll after the
Release Please job creates or updates its PR. For example, have `release.yml` dispatch a
separate, least-privileged merge workflow after the Release Please action returns a PR,
or add a bounded poll for the eligible PR before treating `count == 0` as the
post-merge-dispatch branch. Preserve the existing exact-SHA CI validation before the
publish dispatch.

## Warnings

### WR-01: Failed test partitions do not produce the promised timing artifact

**File:** `scripts/ci/run_test_matrix.sh:21-58`

**Issue:** `set -e` is active and `run_partition` ends with `[[ $status -eq 0 ]]`.
When a partition fails, the function returns non-zero and the script exits at the call
site before lines 57-58 serialize `records`. CI uploads the timing path under
`if: always()`, but the file is absent precisely on failures. This removes the most useful
timing/failure evidence and makes the new artifact contract misleading.

**Fix:** Run every requested partition while accumulating an overall status, always write
the JSON in a `trap` or a finalization block, then exit with the accumulated status after
the artifact has been written. Include each failed partition's exit status in the JSON.

### WR-02: GitHub release is published before Hex publication is known to have succeeded

**File:** `.github/workflows/release.yml:126-146`

**Issue:** The workflow creates the public GitHub release and tag at lines 126-142 before
calling `mix hex.publish --yes` at line 146. A transient Hex failure, rejected package,
or package preflight mismatch therefore leaves a public release/tag that asserts a version
which was not published. A retry can publish it later, but the interval is externally
inconsistent and can confuse release consumers or automation that follows GitHub tags.

**Fix:** Publish the verified package first, then create the GitHub release/tag only after
Hex succeeds; alternatively, mark the release explicitly as draft until publication
returns successfully and publish it afterwards. Keep the target-SHA equality check for an
existing tag/release so retries remain safe.

## Positive checks

- The token endpoint extraction retains the stable `Lockspire.Protocol.TokenExchange`
  facade and routes authorization-code, device-code, and CIBA exchanges through distinct
  coordinators while retaining shared validation and issuance support.
- Protocol key retrieval defaults now point to the Lockspire repository adapter rather
  than leaking a host Ecto repo into protocol modules; the adapter owns the configured
  host-repository interaction.
- Private-JWK decoding is centralized in a safe term/JSON decoder and preserves failure
  normalization to `:invalid_signing_key`.
- Immutable action pins, dependency lock checks, PostgreSQL digest pins, and exact
  post-merge SHA/CI validation materially strengthen the release surface once the
  auto-merge handoff is made reliable.
