## Assumptions

### Repository Facade and Aggregate Ownership
- **Assumption:** `Lockspire.Storage.Ecto.Repository` remains the compatible, configured-repository facade while aggregate-specific Ecto collaborators take ownership of their own records, queries, mappings, and persistence operations.
  - **Why this way:** The current 2,362-line adapter implements fifteen storage behaviors in one module (`lib/lockspire/storage/ecto/repository.ex:1-70`) across clients, interactions, consents, tokens, keys, device/CIBA authorizations, audit, transactions, and replay state. Existing callers and the Phase 134 compatibility manifest explicitly require facade exports such as `replace_client_registration/4`, `redeem_initial_access_token/2`, `transact/1`, and `append_audit_event/1` (`test/lockspire/architecture_fitness_test.exs:45-55`), while all behavior contracts are already aggregate-shaped (`lib/lockspire/storage/token_store.ex:1-46`, `lib/lockspire/storage/client_store.ex:1-28`, `lib/lockspire/storage/key_store.ex:1-31`).
  - **If wrong:** Moving callers directly to new Ecto modules or changing the configured-repo lookup would break existing custom-store/facade callers and violate the v1.x public compatibility baseline even if individual SQL operations still work.
  - **Confidence:** Confident

### Atomicity and Locking Boundaries
- **Assumption:** Each aggregate split retains the present facade-level transaction and row-lock boundaries; operations which compose a state transition with audit persistence remain one rollback domain.
  - **Why this way:** Repository client replacement and RAT rotation take `FOR UPDATE` locks and append audit before the transaction completes (`lib/lockspire/storage/ecto/repository.ex:117-169`); generic `transact/1` delegates to the configured Ecto repo (`lib/lockspire/storage/ecto/repository.ex:332-343`); `transact_with_audit/2` rolls back both work and audit on either failure (`lib/lockspire/storage/ecto/repository.ex:626-639`). Authorization-code redemption locks the code and refresh rotation uses a dedicated database transaction (`lib/lockspire/storage/ecto/repository.ex:1238-1284`), and signing-key activation/retirement use locked state transitions (`lib/lockspire/storage/ecto/repository.ex:1197-1229`). Existing repository tests characterize refresh-family revocation on reuse and guided key transitions (`test/lockspire/storage/repository_test.exs:587-706`, `test/lockspire/storage/repository_test.exs:814-865`).
  - **If wrong:** A concurrent code redemption could mint multiple access tokens, refresh-token replay could fail to revoke the whole family, or a DCR/key state update could commit without its required audit record.
  - **Confidence:** Confident

### Stable Token Facade and Collaborator Boundaries
- **Assumption:** `Lockspire.Protocol.TokenExchange` stays the sole public dispatch/result-conversion facade; its internals should be split by responsibility behind the already-established per-grant owners rather than changing grant entry points or public structs.
  - **Why this way:** The facade dispatches the five supported grants and translates neutral results into retained `%TokenExchange.Success{}` / `%TokenExchange.Error{}` shapes (`lib/lockspire/protocol/token_exchange.ex:10-115`). Phase 134 locked this as the one-way public boundary and verifies exact exports/struct fields (`.planning/phases/134-architecture-topology/134-10-PLAN.md`, Task 1; `test/lockspire/protocol/token_exchange_test.exs:86-120`). Grant coordinators already separate authorization-code, device, CIBA, refresh, and RFC 8693 routing, but `Internal.GrantSupport` still owns authentication, resource validation, issuance, persistence, audit, and failure emission (`lib/lockspire/protocol/token_exchange/internal/grant_support.ex:1-32`, `1210-1275`, `1390-1590`), while refresh independently duplicates transaction/audit capability negotiation (`lib/lockspire/protocol/token_exchange/internal/refresh_exchange.ex:220-310`).
  - **If wrong:** Relocating the public conversion boundary or reusing public facades internally would reintroduce the Phase 134 token dependency cycle or change OAuth response tuple/struct shapes for endpoint and worker callers.
  - **Confidence:** Confident

### Explicit Dependency Bundles and Existing Injection
- **Assumption:** Internal token collaborators should receive a typed, explicit bundle of the storage, signer, policy, clock, telemetry, and sender-constraint dependencies they need, with a compatibility adapter accepting the present request `:opts` injection keys during v1.x.
  - **Why this way:** Current internals independently read individual option keys with default `Repository` modules (`lib/lockspire/protocol/token_exchange/internal/grant_support.ex:1233-1265`, `lib/lockspire/protocol/token_exchange/internal/access_token_signer.ex:109-205`, `lib/lockspire/protocol/token_exchange/internal/rfc8693_exchange.ex:197-256`). They also choose transaction/audit behavior using `function_exported?/3` at runtime (`lib/lockspire/protocol/token_exchange/internal/grant_support.ex:1483-1579`; `lib/lockspire/protocol/token_exchange/internal/refresh_exchange.ex:263-306`). Those injection keys are used by current tests and are therefore a compatibility surface even though the new bundle is internal.
  - **If wrong:** Removing the existing option-based injection abruptly would break deterministic/custom-store tests and advanced host integrations; retaining capability sniffing would leave unsupported combinations to fail only on production paths and prevent COH-04 from being enforceable.
  - **Confidence:** Likely
  - **Alternatives considered:** Keep a keyword option bag indefinitely (preserves flexibility but leaves capability discovery implicit); introduce new required public configuration (would break v1.x callers); normalize legacy options once at the stable facade into an internal bundle (recommended).

### Characterization as the Refactor Contract
- **Assumption:** The Phase 135 proof should characterize observable endpoint-level success and failure outcomes plus persisted audit and telemetry for authorization-code, refresh, device, CIBA, and token-exchange flows, instead of treating module/line movement as sufficient evidence.
  - **Why this way:** Existing capability tests already assert public facade routing/struct compatibility (`test/lockspire/protocol/token_exchange_test.exs:48-120`), authorization-code replay plus audit/telemetry (`test/lockspire/protocol/token_exchange/authorization_code_test.exs:624-718`), refresh-reuse error/audit behavior (`test/lockspire/protocol/refresh_exchange_test.exs:516-573`), device redemption audit behavior (`test/lockspire/protocol/token_exchange/device_code_test.exs:614-617`), and RFC 8693 behavior (`test/lockspire/protocol/rfc8693_exchange_test.exs`). Phase 134 explicitly established that graph-green alone is not evidence for OAuth refactors (`.planning/phases/134-architecture-topology/134-CONTEXT.md`, D-13), and its verifier retained the public result shapes as an executable contract (`.planning/phases/134-architecture-topology/134-VERIFICATION.md`).
  - **If wrong:** A split could preserve compilation and internal unit outcomes while changing wire errors, token contents, audit attribution, or telemetry consumed by operators and downstream observability.
  - **Confidence:** Confident
