## Assumptions

### CI Evidence and Security Scanning
- **Assumption:** CI-01 should add a fail-closed, low-severity Sobelow gate that explicitly scans both `Lockspire.Web.Router` and `Lockspire.Web.AdminRouter`, with only narrow, named, reviewed exclusions; it must not infer router coverage from the existing application-wide quality alias.
  - **Why this way:** The current fast job runs `mix qa`, docs, dependency audit, package build, and the fast matrix, but contains no Sobelow invocation ([`.github/workflows/ci.yml:138-151`](../../../.github/workflows/ci.yml)). The library exposes distinct public and operator routers, whose intended separation is executable in [`test/lockspire/web/admin_router_test.exs:4-59`](../../../test/lockspire/web/admin_router_test.exs); the generated host also mounts those routers separately ([`test/lockspire/install/verify_test.exs:60-64`](../../../test/lockspire/install/verify_test.exs)).
  - **If wrong:** A scanner configured against one router or only broad source paths could pass while a new low-severity issue in the unscanned admin or public HTTP surface reaches a release.
  - **Confidence:** Confident

- **Assumption:** CI-03 should extend existing immutable dependency and topology evidence instead of introducing a second, partly overlapping dependency policy: it must reject newly unused locked dependencies and invoke the established cycle command, while controlled adoption-demo updates retain its checked-in lockfile and minimum-version fixtures remain untouched.
  - **Why this way:** CI currently uses `deps.get --check-locked` and verifies all four known lockfiles after release-hygiene setup ([`.github/workflows/ci.yml:67-71`](../../../.github/workflows/ci.yml)), while compatibility separately installs and rechecks the immutable Phoenix/LiveView fixture lock ([`.github/workflows/ci.yml:234-243`](../../../.github/workflows/ci.yml)). The existing cycle probe is intentionally a small, failing script ([`scripts/ci/check_architecture_topology.sh:1-14`](../../../scripts/ci/check_architecture_topology.sh)), but it is not called by the shown CI fast/integration jobs.
  - **If wrong:** A new compile-connected cycle or a dead direct dependency can be merged despite the architecture and locked-fixture claims, or a dependency refresh can silently change the minimum-support fixture being advertised.
  - **Confidence:** Likely

### Coverage Aggregation and Test Ownership
- **Assumption:** CI-02 needs one authoritative complete-suite coverage report made from the already-disjoint fast and integration partitions, rather than raising the current fast-only 73% threshold or double-running partitions merely to obtain a percentage.
  - **Why this way:** `mix.exs` configures built-in coverage at 73%, and its `test.coverage` alias runs ordinary `mix test --cover` ([`mix.exs:27, 87`](../../../mix.exs)); the contract explicitly describes that as the ordinary *fast-suite* denominator ([`test/lockspire/coverage_baseline_contract_test.exs:7-30`](../../../test/lockspire/coverage_baseline_contract_test.exs)). The workflow separately runs fast with coverage ([`.github/workflows/ci.yml:150-159`](../../../.github/workflows/ci.yml)) and integration plus clean-room proof ([`.github/workflows/ci.yml:313-322`](../../../.github/workflows/ci.yml)); the runner's integration mode itself executes both `test.integration` and `test.clean-room.e2e` ([`scripts/ci/run_test_matrix.sh:57-60`](../../../scripts/ci/run_test_matrix.sh)).
  - **If wrong:** The proposed 84% number may be a misleading fast-only figure, exclude the clean-room suites, or inflate evidence by running overlapping tests more than once.
  - **Confidence:** Confident

- **Assumption:** Coverage artifacts and timing/evidence uploads are immutable-output inputs only: aggregation should consume exported reports from the exact jobs and ref being evaluated, and should not restore, rewrite, or execute code carried in a cache or artifact.
  - **Why this way:** The current jobs upload timing JSON only after each runner writes it before exit ([`scripts/ci/run_test_matrix.sh:63-73`](../../../scripts/ci/run_test_matrix.sh); [`.github/workflows/ci.yml:153-159, 316-322`](../../../.github/workflows/ci.yml)), while dependency caches are keyed by lockfiles ([`.github/workflows/ci.yml:116-124, 283-299`](../../../.github/workflows/ci.yml)). The clean-room fixture independently checks package inventory, rejects symlinks and test support, and rejects a vendored package resolving to the live checkout ([`scripts/acceptance/clean_room/package_input.py:75-90, 117-136`](../../../scripts/acceptance/clean_room/package_input.py)).
  - **If wrong:** A mutable cache/artifact can become an unreviewed execution or package input, so coverage can attest to code other than the checked-out release candidate.
  - **Confidence:** Likely

### Conformance Inputs and Supplemental Evidence
- **Assumption:** CONF-01 must replace every mutable OIDF suite input with a checked-in immutable identity (image digest, source revision, downloaded-file checksum), and must fail closed rather than use the present `latest`/`master` fallback.
  - **Why this way:** Both suite scripts default the image tag to `latest` ([`scripts/conformance/run_phase37_suite.sh:10-15`](../../../scripts/conformance/run_phase37_suite.sh); [`scripts/conformance/run_fapi2_suite.sh:10-15`](../../../scripts/conformance/run_fapi2_suite.sh)), then download compose and Python files from GitLab `master` ([`scripts/conformance/run_phase37_suite.sh:51-61, 200-203`](../../../scripts/conformance/run_phase37_suite.sh)). The checked-in JSON plans pin plan names and variants but not an upstream suite revision or digest ([`scripts/conformance/fapi2-plan.json:1-17`](../../../scripts/conformance/fapi2-plan.json)).
  - **If wrong:** A rerun can execute a changed upstream suite while retaining the same Lockspire revision and label, making a conformance result irreproducible or concealing a supply-chain change.
  - **Confidence:** Confident

- **Assumption:** CONF-02 should keep conformance non-blocking and explicitly scheduled, upload only redacted evidence, and avoid certification claims; hosted credentials and external URLs must remain secret inputs that cannot enter retained logs/configuration.
  - **Why this way:** The workflow is only dispatch-triggered even though its hosted job tests `github.event_name == 'schedule'` ([`.github/workflows/oidf-conformance.yml:3-10, 125-155`](../../../.github/workflows/oidf-conformance.yml)), so there is presently no scheduled trigger. It uploads raw `.artifacts/conformance/*` on every outcome ([`.github/workflows/oidf-conformance.yml:67-72, 118-123, 173-178](../../../.github/workflows/oidf-conformance.yml)); suite scripts copy provider config and logs into those directories ([`scripts/conformance/run_phase37_suite.sh:155-156, 318-365`](../../../scripts/conformance/run_phase37_suite.sh)). The maintainer guide declares the external lane optional and not a release gate or certification proof ([`docs/maintainer-conformance.md:104-117`](../../../docs/maintainer-conformance.md)).
  - **If wrong:** A scheduled run either never executes, leaks hosted provider/credential context into artifacts, or converts supplemental test output into an unsupported certification/release assertion.
  - **Confidence:** Confident

### Release Artifact and Clean-Room Proof
- **Assumption:** REL-01 should treat the pre-publish local Hex artifact and the post-publish exact public version as two distinct evidence sources, each running the existing clean-room provider/client HTTP journey rather than the current compile-only post-publish script.
  - **Why this way:** Phase 133 explicitly deferred exact pre/post-publish Hex verification to this phase ([`.planning/phases/133-clean-room-saas-journey/133-CONTEXT.md:14-16`](../../../.planning/phases/133-clean-room-saas-journey/133-CONTEXT.md)). The clean-room harness already builds and unpacks a Hex-style package before starting a child ([`scripts/acceptance/clean_room/package_input.py:93-104`](../../../scripts/acceptance/clean_room/package_input.py)) and uses isolated child roots/locks ([`scripts/acceptance/clean_room/package_input.py:117-167`](../../../scripts/acceptance/clean_room/package_input.py)); its documented entrypoint says it owns only provider and confidential-client roles ([`scripts/acceptance/run_clean_room_saas_journey.sh:3-29`](../../../scripts/acceptance/run_clean_room_saas_journey.sh)). In contrast, the release job preflight only builds/dry-runs/docs ([`.github/workflows/release.yml:144-152`](../../../.github/workflows/release.yml)) and the post-publish script creates a Phoenix app, fetches dependencies, and compiles—no migrations, `lockspire.verify`, boot, or HTTP journey ([`scripts/publish/verify_install_truth.sh:69-92`](../../../scripts/publish/verify_install_truth.sh)).
  - **If wrong:** Publication can succeed with only a compile check, leaving a broken installed package, migration path, generated configuration, or live OAuth/OIDC path undetected.
  - **Confidence:** Confident

- **Assumption:** REL-02 should generate a redacted manifest from the exact detached release SHA and built tarball, verify the post-publish Hex release checksum against that same tarball, and retain the manifest/artifacts without allowing them back into package or runtime inputs.
  - **Why this way:** The publish job detaches and verifies the release SHA before build/publish ([`.github/workflows/release.yml:128-148`](../../../.github/workflows/release.yml)); the idempotent publisher computes the tar SHA-256 and compares it to Hex's release API checksum when the version already exists ([`scripts/publish/publish_hex_idempotently.sh:4-42`](../../../scripts/publish/publish_hex_idempotently.sh)). However the post-publish verification currently queries package metadata only for version existence ([`scripts/publish/verify_install_truth.sh:25-54`](../../../scripts/publish/verify_install_truth.sh)), and the artifact-policy test prohibits retained repository-local artifacts from becoming package inputs ([`test/lockspire/repository_artifact_policy_contract_test.exs:8-18`](../../../test/lockspire/repository_artifact_policy_contract_test.exs)).
  - **If wrong:** A successful post-publish run can attest to an available version without proving it is byte-identical to the reviewed tarball, while a retained manifest could accidentally leak secrets or contaminate the package boundary.
  - **Confidence:** Confident

### Hidden Dependencies and Immutable-Input Boundaries
- **Assumption:** The phase must make hidden external prerequisites visible and fail closed: GitHub protected-environment policy, Hex/GitHub APIs, PostgreSQL, Docker/Compose, Python, `jq`, and the OIDF host bridge are trusted execution dependencies, not evidence of a package's behavior.
  - **Why this way:** Release security depends on the `hex-publish` environment and its `HEX_API_KEY` ([`.github/workflows/release.yml:118-152`](../../../.github/workflows/release.yml)); repository docs say that deployment restriction and secret placement live in GitHub settings rather than the repo ([`docs/maintainer-release.md:111-120`](../../../docs/maintainer-release.md)). Clean-room verification fails before child setup unless Mix, Postgres, and a loopback listener exist ([`scripts/acceptance/clean_room/package_input.py:25-56`](../../../scripts/acceptance/clean_room/package_input.py)), while external suites require Docker, Python, curl, and Mix ([`scripts/conformance/run_phase37_suite.sh:196-203`](../../../scripts/conformance/run_phase37_suite.sh)).
  - **If wrong:** A green result can depend on mutable CI/environment state that cannot be reconstructed, or an absent tool/secret can be mistaken for protocol failure instead of a clearly classified infrastructure failure.
  - **Confidence:** Confident

## Needs External Research
- The authoritative OIDF Conformance Suite immutable distribution model: acceptable image digests, source tag/commit availability, and whether official release assets publish stable checksums for every downloaded compose/script file.
- ExUnit/Elixir built-in coverage export and merge semantics for the pinned Elixir 1.19.5 / OTP 28 toolchain, including how to make one truthful fast-plus-integration denominator without re-executing tests.
- Hex API checksum encoding and release/tarball endpoints needed to compare the exact published package bytes after first publish, rather than relying on version-list metadata.
