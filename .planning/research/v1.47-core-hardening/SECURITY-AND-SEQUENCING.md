# Security and Sequencing Research: v1.47 Core Interoperability & Hardening

**Project:** Lockspire
**Researched:** 2026-10-24
**Confidence:** HIGH for repository baseline; MEDIUM for standards interpretation and milestone sequencing

## Recommendation

Keep v1.47 as a focused OAuth/OIDC Core interoperability and hardening milestone. Make its acceptance a bounded standards-led audit of the already-supported core surface, with concrete failing/ambiguous cases selected from current evidence; do not turn it into a rewrite or a claim of certification. Run the dedicated `client_secret_jwt` verifier-key lifecycle as a distinct v1.48 milestone after v1.47 establishes the security baseline and regression evidence. Keep token lifecycle concurrency work conditional on a reproduced race or unproven invariant. Keep OPS-03 and KEK-04 as candidates with evidence triggers, not promised follow-ons.

This sequence protects review capacity: v1.47 establishes the interoperability truth; v1.48 changes at-rest key custody and needs its own migration/rotation proof. Bundling both makes it harder to tell whether an interoperability regression came from protocol changes or a new verifier-storage path.

## Evidence: Current State

- The policy module seals `client_secret_jwt` verifier material with `Plug.Crypto.encrypt/3`, using the endpoint `secret_key_base` and a fixed application salt, and its legacy lookup reads Lockspire endpoint configuration ([`policy.ex`](../../../lib/lockspire/security/policy.ex)). - Signing-key maintenance already supports dry-run, apply, status/check, key rotation ordering, audit, per-row conflict handling, and overlapping re-encryption runs ([`keys.ex`](../../../lib/lockspire/admin/keys.ex), [`lockspire.keys.reencrypt`](../../../lib/mix/tasks/lockspire.keys.reencrypt.ex), [`reencrypt_concurrency_test.exs`](../../../test/lockspire/storage/reencrypt_concurrency_test.exs)). Therefore OPS-03 is an operational scaling refinement, not the prerequisite for SEC-01 or a missing general key-rotation foundation.
- Refresh exchange locks current client state, delegates token rotation to the selected token store inside an audited transaction, maps a detected reuse to `invalid_grant`, and emits durable replay/family-revocation events ([`refresh_exchange.ex`](../../../lib/lockspire/protocol/token_exchange/internal/refresh_exchange.ex), [`grant_persistence.ex`](../../../lib/lockspire/protocol/token_exchange/internal/grant_persistence.ex)). Do not describe a refresh race as a present defect without reproducing one against the selected store and supported PostgreSQL/runtime combination.

## Standards and Ecosystem Reading

Primary references read on 2026-10-24:

- [RFC 9700, OAuth 2.0 Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700.html), published January 2025. Relevant subjects include exact redirect matching, PKCE, token replay prevention, client authentication, refresh-token family rotation, and refresh token scope/resource binding. It explicitly notes that best practices can expose interoperability incompatibilities; phase acceptance should record compatibility behavior rather than silently loosening defaults.
- [RFC 7523, JWT Profile for OAuth 2.0 Client Authentication and Authorization Grants](https://www.rfc-editor.org/rfc/rfc7523.html), May 2015. Client assertions require issuer, subject (`client_id`), audience identifying the authorization server, and expiry. `jti` is optional in the profile; the server may use it to prevent replay. Lockspire's required, durably recorded JTI is a stricter local security profile, so interoperability tests should make the stricter contract explicit. The RFC does not prescribe how an authorization server stores its client shared secret.
- [OpenID Connect Core 1.0, incorporating errata set 2](https://openid.net/specs/openid-connect-core-1_0.html), final publication dated December 15, 2023, defines core protocol behavior and client authentication. [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) is the separate metadata specification; its `token_endpoint_auth_methods_supported` and related fields help compare advertised capabilities with endpoint behavior.
- [Plug.Crypto 2.1.1 documentation](https://plug.hexdocs.pm/Plug.Crypto.html), official package documentation (version observed in search results). It documents encrypt/decrypt functions based on a key base and salt, consistent with the current coupling seen in Lockspire. It does not provide the dedicated multi-key envelope/rotation contract SEC-01 calls for.

These sources support a protocol checklist and clarify that key custody is a local product design decision. They do not establish a need for a KMS adapter, a new crypto dependency, or certification. Confidence is MEDIUM because this is a targeted reading, not a full conformance test run or cross-implementation matrix.

## Proposed Milestone Boundaries and Acceptance

### v1.47 — OAuth/OIDC Core Interoperability & Hardening

Treat these as scope proposals for the next requirements discussion, not approved requirements:

- Start with a traceable supported-surface inventory and standards checklist. Focus on behavior agreement among metadata/discovery, endpoint validators, success/error responses, and current docs/examples. Prioritize authorization-code + PKCE and OIDC Core behavior already claimed by Lockspire.
- Change only behavior backed by a reproducible interoperability or security finding. Preserve PKCE S256, exact redirect URI matching, no implicit response, `alg=none` rejection, existing FAPI boundaries, and host ownership of accounts/login/claims policy.
- Acceptance should identify exact request/response cases, tested supported dependency versions, storage adapter assumptions, and regression boundaries. For each fixed finding, include a positive interoperable case and a negative/adversarial case, with live runtime proof where browser/DB behavior matters.
- Align discovery, supported-surface docs, examples, and runtime truth; record unsupported or conditional behavior plainly. Supplemental findings stay labeled supplemental. Passing the suite is not OIDF certification or a zero-defect promise.
- Exit trigger: every included finding has an owner, reproducer, exact accepted behavior, and automated proof; excluded findings have an explicit disposition. If baseline finds no material residual core issue, stop at sustainment rather than expand scope.

Exclude from v1.47 by default: dedicated verifier-key migration, KMS/Vault, generic grant-family rewrite, new flow families, broad certification sweeps, UI redesign, and performance optimization without measurements.

### v1.48 — SEC-01 Dedicated `client_secret_jwt` Verifier Key

Suggested vertical slice: configuration and install/upgrade guidance → dedicated-purpose key envelope and dual-read/rewrap strategy → runtime verification across every supported direct-client endpoint → operator status/rotation/loss recovery → packaged upgrade proof.

Acceptance should cover:

1. New verifier material is sealed under a dedicated rotatable key configuration; new writes use the current ID, reads resolve the envelope’s key ID, ciphertext/AAD tampering and unknown IDs fail closed, and errors/audit/logs reveal no credential material.
2. Existing Plug.Crypto-sealed rows remain readable during the explicit compatibility window. Migration/rotation uses a safe dual-read then rewrap/check then reject-old-format sequence with one canonical stored representation at completion. Deploy steps require every host node to know the new read key before any node begins writing with it.
3. Add tests for no key, wrong key, retired-key removal before migration, mixed old/new-key rows, concurrent rewrap against verifier rotation/update, database write failure, and operator recovery. Preserve current client secret hash semantics; do not change client auth API or expose raw verifier values.
4. Specify key-loss behavior: if neither old endpoint `secret_key_base` nor dedicated read key is available, affected `client_secret_jwt` clients cannot authenticate until their secret is rotated/reprovisioned. Do not silently accept old ciphertext, fall back to weaker auth, delete rows, or claim that ciphertext can be recovered without its key.
5. Keep host policy/config ownership at the host boundary. The library should validate/configure an explicit provider/key set, not require a standalone service. Preserve signing-key and verifier-key domain separation even if they share reviewed AES-GCM implementation code; keys must not be reused across cryptographic purposes by default.

These requirements need their own phase-specific design because the current client field is `text` (`client_secret_jwt_verifier_encrypted`), so the envelope can likely fit without a schema rewrite, but storage conversion, custom storage callbacks, and mixed-version deployment behavior still require inspection during planning.

## Threats and Failure Modes to Carry into Planning

- **Shared endpoint secret coupling:** rotating or losing host `secret_key_base` may break verifier decryption; accidental reuse of that secret for other Plug purposes increases blast radius. The exact operational impact depends on host key management; no exploit was reproduced here.
- **Mixed-version rollout:** a new node writing envelopes unknown to an old node can cause verifier authentication failures. All nodes need read support and keys before switching current writes.
- **Premature old-key removal:** rewrap status may be incomplete or partial; deleting old IDs can strand clients. Status must be based on all relevant client rows, not only active clients unless inactive-row disposition is explicit.
- **Encryption as a false control:** encryption does not protect verifier plaintext from a compromised running host that can access its in-memory key. The purpose is database/backups separation and independent rotation, not protection from arbitrary host-code execution.
- **Key loss:** authenticated ciphertext cannot be recovered without its exact key. Fail closed and give operators a rotate/reprovision path with clear affected-client scope; do not log ciphertext or raw secrets.
- **Distributed rotation:** a shared Postgres database does not ensure each node has identical key IDs. Configuration parity, rolling deploy order, read/write compatibility, audit, and retry-safe rewrap need explicit proof.
- **Refresh-token races and client retry:** parallel legitimate refreshes can resemble replay under rotation; the correct result may revoke the family by design. Do not weaken reuse containment to make retries easier without an explicit protocol/product policy. Verify serializable outcomes and audit atomically.
- **Remote key provider availability:** KMS/Vault lookups on critical token paths add latency, transient failure modes, IAM drift, and bootstrap dependencies. Use a measured requirement and explicit host-controlled outage/caching contract before integration.
- **Paged maintenance:** keyset pagination must be stable while rows change; status/check and apply must not imply one snapshot if they are not transactional. A partial page failure must preserve useful progress without hiding failed IDs or secrets.

## Dependency Policy

For these slices, prefer the existing `Plug.Crypto` and OTP `:crypto` primitives already in the dependency tree, with small local orchestration that is easier to audit than a general secrets framework. The existing envelope implementation is already a reviewed local abstraction with test coverage; SEC-01 should not fork a second cipher format casually. Maintain vetted crypto primitives as dependencies when they materially improve correctness; do not vendor cryptographic code. Add a package only for a demonstrated capability gap, supported maintenance/security history, and a clear transitive-dependency budget. A Vault/KMS client is a later adapter decision and should not be added as a transitive dependency to the core library absent adopter evidence.

## Sequencing and Stop Rules

1. **v1.47 core interoperability** — fixes demonstrated supported-core inconsistencies and makes support claims executable.
2. **v1.48 SEC-01** — follows because independent verifier key rotation is valuable and concrete, but changes persistence/read/write migration behavior and deserves separate review.
3. **Token concurrency slice** — insert only when a concrete race, selected-store contract gap, or required distributed proof is identified; keep narrow and outcome-driven.
4. **OPS-03 / KEK-04** — revisit only at their triggers. They are lower value than protocol truth and verifier key isolation until scale/operator evidence says otherwise.
5. **Stop or sustain** after these slices if remaining work is parity, theoretical certification breadth, or infrastructure optionality without adopter evidence.

Do not pre-authorize v1.48 or later work solely because it appears in this proposed order.

## Adversarial Review of a Broad Bundled v1.47

The broad proposal is attractive because OAuth/OIDC support spans endpoints and standards interact. Its failure modes are equally real: “Core” may quietly pull in every optional extension; a single umbrella milestone can mix protocol changes, storage migration, maintenance scaling, and KMS outages into one hard-to-debug risk bundle; certification language can outrun the actual tests; and an enormous conformance matrix can consume maintainer time without improving the adopter story. The strongest counterargument to sequencing SEC-01 second is that `secret_key_base` coupling is already a concrete design concern. The reason to separate it is not low importance: it is to isolate backward-compatible data migration and key-loss decisions from the v1.47 runtime behavior audit. If the audit shows that this coupling is already causing operational failure or materially raises exposure in a supported deployment, bring SEC-01 forward and narrow v1.47 accordingly.

Research also has diminishing returns: standards reading can enumerate MUST/SHOULD text, but it cannot decide Lockspire’s supported subset, host-specific claim semantics, custom storage compatibility, or which interoperability failures adopters actually encounter. Those choices need a repository baseline, focused fixtures, and phase requirements tied to real surfaced behavior. Avoid more broad ecosystem surveys unless a specific supported case remains disputed.
