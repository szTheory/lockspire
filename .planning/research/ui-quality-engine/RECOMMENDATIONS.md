# Lockspire UI quality engine: reviewed recommendation

**Date:** 2026-10-25. **Source:** `a92bd9f753d30bb97be147c2a2ce532e442149d4`. **Status:** planning proposal; implementation and milestone selection are not authorized by this artifact. [Inventory](INVENTORY.md) · [Sequencing proposal](MILESTONE-PROPOSAL.md).

## Direction and durable owner intent

Make the real operator UI easy to inspect from components through complete jobs, with realistic difficult data, fast mechanical feedback and bounded visual review. The goal is intentionally designed, calm, coherent software: readable typography, professional hierarchy, restrained color, useful affordances, consistent domain language, natural navigation and efficient common/expert workflows. Mobile-first reflow, light/dark parity and accessible state changes are standing expectations. “Award-winning” and “iPhone-designed” describe the craft ambition, not certification, a new visual identity, ornamental animation or a numeric quality target.

The owner requested this direction on 2026-10-25, including aggressive pruning of impossible stories, plausible synthetic adopter situations and a rolling re-evaluation of milestone ordering. The supplied methodology is an input to adapt, not an implementation specification. File provenance: `~/Documents/ui-storybook-stresstest-methodology-prompt.txt`, SHA-256 `2df5733d4896899613c70101507e8a991b3a3ddda3d0ce8e699cd24ad7c3e0ee`. This document preserves its useful intent without requiring that personal file to exist for future work.

**Owner clarification, 2026-10-25:** new milestones continue through the full applicable GSD ceremony; this research does not replace `$gsd-new-milestone`, requirements/roadmap approval, phase planning/checking, execution, verification/review or audit/closeout. The selected story tool is **`phoenix_storybook`**, not a custom equivalent. Use its discovery, variations, navigation and render facilities; write only Lockspire-specific scenarios, component adapters and small manifest/check integration helpers. Exact release selection and compatibility proof remain future GSD research tasks. This clarification strengthens the proposal without opening a milestone or authorizing product changes.

Use **Operate** mode. Preserve Signal Cyan, the surface-specific accent split, system-selected appearance, existing font stacks and robust local fallbacks. No downloaded fonts, new public theming API, host-wide reset, new OAuth operation, public lab or CIAM scope. Product truth remains [PRODUCT.md](../../../PRODUCT.md), [supported surface](../../../docs/supported-surface.md) and current code. The published package has real UI, so the methodology's applicability exit does not apply.

## Story admission, composition and pruning

The tree uses familiar nouns: **Overview, Apps, App registration, App setup tokens, Security, Keys, Consents, Tokens, Sign-in requests, Device authorization requests, App sign-out notices**. Journey metadata stays Orient/Configure/Support/Operate; avoid exposing internal names such as `ClientsLive`, DCR or IAT as story navigation. Reference the existing scorecard instead of maintaining a second job catalogue.

A useful branch might be `Apps / App details / Credentials / Rotate client secret / Validation error`. It reuses the real production component at each relevant level. The page variation is “Provider operator replaces a partner app's secret; confirmation is missing and the draft remains visible,” not “red + disabled + long.” Screens share the actual presentation code with production; story-only copies of page markup are prohibited.

Each manifest entry records stable scenario/story/variation IDs, level, production caller/source, scorecard/job, operator persona, adopter profile, situation, expected state/actions, fixture version/time, container constraints and selected dimension coverage. Rendering metadata records source SHA, story adapter version, browser/OS/font environment and effective theme. A generated manifest is committed and checked for drift under the exact environment and pinned Storybook release that expose its API. Do not hardcode undocumented per-variation URLs.

Admit a state only if a real caller, domain branch or supported failure path can produce it. Cover first use, empty versus no match versus failed observation, one/many/page boundary, validation, consequential action and recovery; include loading only for a real asynchronous state. Large totals should not mean thousands of rendered rows. Include realistic long values, mixed scripts, accepted IDN/Unicode inputs and missing optional fields where the domain accepts them. Mixed Arabic content does not imply a localized RTL admin or unsupported URI acceptance.

Prune when the app cannot render the combination, the domain forbids it, its output is equivalent to an existing case or it serves no job. Record disposition and surviving scenario ID so removed evidence does not silently disappear. Keep deliberately malformed/fallback **unit tests** even when their impossible screen story is removed. Test immutable names/URLs at the real backend limits; shorten an authored nav label rather than defending a contrived long translation that the product does not have. Do not truncate useful operator data merely to make a screenshot attractive.

Port the maintainer stress review surface after parity, then retire duplicate browsing/markup. Retain route scorecards, semantic/unit tests, connected-host proof, brand/token documentation and historical evidence: they serve different purposes. Do not delete illustrative brand examples or an adopter-visible surface just because they contain components.

## Presentation boundaries and the maintainer host

Keep LiveView mount, parameter handling, loading, policy, events and mutation ownership intact. Extract selected render bodies or meaningful areas into ordinary function components accepting explicit data, forms, state and navigation/action inputs. Preserve `phx-*` event names, component IDs, validation retention, error targets, slots, focus and patch behavior. Existing `client_form/1`, `rotation_panel/1` and `lifecycle_actions/1` demonstrate useful seams; their module names do not make them stateful LiveComponents. Current admin source has no streams; future stream-backed pages require a deliberate adapter rather than socket mocks.

DB-free stories render those same components from scenario adapters. A host adapter may supply inert URLs/actions for isolated inspection; the production caller still supplies actual paths and events. A story with a visible control is not proof its action works. A short connected route set must exercise initial HTTP and LiveView joins, params/navigation, submit → error → correction → success, repeated actions, focus restoration, reconnect and host authorization. Denied host entry belongs to this connected proof unless a real library presentation branch exists. Preserve queue read-only behavior.

Recommend **one Storybook backend in the adoption demo, available only in dev/test**, rather than a second standalone host initially. Put its backend/scenario compilation outside production source paths and gate imports, route expansion and assets at compile time. The demo currently starts Repo/Oban: DB-free **rendering** does not promise DB-free **host boot**. Add a minimal host only if measured startup/iteration cost justifies another application/router/endpoint.

Today the library compiles `test/support` only in `:test`; a demo path dependency normally compiles the library in `:prod`. Therefore explicitly include a shared maintainer-only scenario source directory in each top-level host's dev/test compilation paths. Do not force the dependency into `env: :test` or leak test modules into library `lib`. Keep scenario definitions outside the library's Hex allowlist; use separate adapters for rendered assigns and disposable demo persistence. Do not run the existing demo seed script for discovery: it truncates tables.

Declare any future `phoenix_storybook` dependency in the **maintainer host only**, restricted to dev/test. It can run as an OTP application there; `runtime: false` is not a synonym for “excluded from published runtime” and must not be set blindly. Pin and test a compatible release, dependency closure, security history and license before installation. Mutable upstream source/documentation returned differing version labels during research; no release is selected or compatibility proven here. Manual scoped setup avoids a generator changing unrelated host files. Disable external icon/font fetching and preserve the real CSS/scripts, CSP and root theme behavior inside isolated bare render frames. Verify theme initialization and LiveView patches; the shell uses document-root state and local storage, so a sandbox class alone is insufficient.

The existing `RouteAssertions.assert_public_package_ceiling!/0` bans “storybook” in library router/mix/support inputs. Preserve that ceiling: no root package dependency, route or support promise. Eventual acceptance must demonstrate production compilation with no Storybook/scenario modules/routes/assets, a package file-list inspection, no new runtime dependency closure and a clean host installation without Node. Development routes bind locally and use synthetic data only. Storybook is a maintainer tool, not an adopter requirement.

## Visual and verbal source of truth

[Brandbook tokens](../../../brandbook/tokens/tokens.json) remain the canonical intended vocabulary; [runtime CSS](../../../lib/lockspire/web/admin_css.ex) is evidence of what ships. Reconcile them explicitly before expanding generation/checking. JSON muted text currently aliases `#64748b`; runtime deliberately uses `#5f6f84` to preserve contrast on muted surfaces. Preserve the contrast-checked shipped outcome and record the reconciled decision. Existing checks compare selected values, not complete parity. Include font fallback lists, named layering and breakpoint metadata as well as color/type/spacing/radius/shadow/focus/motion roles.

Generate or check the existing CSS variables with small local helpers and semantic metadata. Do not reset host CSS or make every structural zero, `none`, pill radius, SVG color and reduced-motion override an illegal token bypass. Introduce scoped exceptions with reasons and stable ownership. Test **allowed, actually used semantic foreground/background pairings**, including focus and controls, in both themes; reuse existing contrast math. Arbitrary Cartesian color pairs are often meaningless. A DTCG migration is optional future interoperability work; the current custom JSON's `value` shape is not the published DTCG `$value`/`$type` format merely because it references a schema.

[PRODUCT.md](../../../PRODUCT.md) owns verbal tokens: vocabulary, retired wording, voice and least-technical-user rule. Extend its guard into story descriptions, authored rendered text and accessible names (`aria-label`, title, placeholder, alt); do not create another glossary. No gettext-based UI pipeline was identified, so do not assume msgids are the only source. Distinguish authored language from app names, URLs, identifiers, code and permitted protocol explanations. “Client ID,” “client secret,” token family and explained PKCE/DPoP/PAR/FAPI/JARM retain their approved uses. Use sentence case, verb-led action buttons, specific errors without “Oops”/exclamation marks and distinct empty/error/confirmation patterns; nav labels and entity links can remain nouns. Avoid blind style rules that remove useful security consequences or diagnostic precision.

## Layered automation and practical limits

**L1 — extend blocking deterministic checks.** Keep current ExUnit/LiveViewTest/LazyHTML, `CssAssertions`, `HtmlAssertions`, package/redaction and vocabulary tests. Add scenario invariants, manifest parity, complete intended token-alias checks and scoped style rules. Source/HTML checks establish structure, not computed layout. Fix a primitive/pattern once and prove all affected callers; do not add one snapshot assertion per page that repeats its markup.

**L2 — one manifest-driven browser observer, measured before becoming a gate.** Reuse CDP, host startup/cleanup, redaction and receipt binding. Read manifest coverage rather than duplicate lists. Observe render errors/unhandled console failures, page overflow, visible text loss, labels/accessibility names, focus/overlays and supported token roles. Expected negative-test errors require explicit scenario expectations; never blanket-ignore console errors. Browse bare isolated render routes and a short genuine connected-job set. Scope standalone-component landmark rules appropriately and test full-page landmarks in page stories.

Dependency recommendation: a development-only pinned **axe-core** is justified for accessibility rules that local geometry helpers cannot replace. Evaluate Playwright only if a bounded comparison shows simpler reliable orchestration than current CDP; no new runner is presumed. Neither is installed by this plan. Keep small contrast/overflow/manifest/target helpers local. Reuse redaction, artifact and cleanup policies; do not build a parallel screenshot service.

Proposed **unmeasured** PR budget: L1 incremental ≤60 seconds; L2 ≤5 minutes warm wall time, at most two shards, ≤8 minutes cold. Measure host startup, case count, p50/p95 case time, CPU-minutes, retries and flake rate first. Begin with observation/triage; enable blocking for confirmed new regressions after the pilot is deterministic. Do not meet the budget by silently skipping a required acceptance class.

Every real variation remains discoverable in the manifest. Each UI PR exercises affected states in light/dark at 320 and desktop; include 375/390 where relevant, representative 768/1280/1440 and actual breakpoint neighborhoods 639/640/641, 799/800/801 and 1119/1120/1121 for affected layouts. New widths such as 375 require an intentional extension of BrowserEvidence's current allowed-width contract; they are proposed coverage, not currently accepted receipt values. Shared CSS/component changes expand affected callers. Whole-page stories use full viewport widths; group stories also use their real narrow containers. Reduced-motion and system-light/system-dark are selected high-value cases, not multipliers on every static badge. A full explicit sweep can run at UI-milestone/pre-merge boundaries if measured cost warrants it; no schedule is created here.

Accessibility checks need faithful interpretation, not a conformance badge:

- 320px page reflow is necessary evidence; useful local two-dimensional tables can scroll. Check information/action reachability too.
- Text contrast normally needs 4.5:1; qualifying large text and meaningful nontext controls/states have different thresholds/exceptions. Observe compositing, not just declared hex values.
- 24px target size has spacing/inline/native/equivalent/essential exceptions. Preserve comfortable incumbent controls; do not shrink to the floor. Review touch use separately from viewport emulation.
- Root-font doubling misses pixel-sized text. Record text enlargement and actual browser zoom as separate tests; neither is proved by a narrow screenshot.
- A focus outline/style change is not proof of visibility, occlusion, contrast or sensible task order. Check scroll/overlay behavior and representative keyboard paths. WCAG 2.4.11 concerns a focused component not being entirely hidden; a stronger fully visible goal can be a product standard.
- axe `incomplete` means review needed, not a confirmed violation or a pass. Track a triage disposition/evidence; unresolved new cases cannot silently disappear into a green summary.
- Normalize shared navigation structure/names/destinations while allowing mount prefix, active `aria-current`, permitted visibility, responsive expansion and job-specific secondary navigation. Identical ARIA snapshots across all pages would reject correct behavior.
- Computed values can be inherited, relative, composited or structural resets. Compare semantic roles and resolved tokens in context, not every number against an unordered list.

**L3 — selected visual baselines.** Capture one meaningful state per section plus its worst credible composition, at selected mobile/desktop widths and both themes. Freeze data/time, pin browser/OS/DPR and available fallback fonts, await `document.fonts.ready`, settle LiveView and disable animation only for capture. Test reduced-motion behavior separately. Scrub secrets **before** capture; masking timestamps must not conceal timestamp-layout defects. Keep approved platform baselines in a maintainer artifact store consistent with the existing image ignore policy, with checksums/metadata in git. Ordinary verification never regenerates expected images. Human acceptance is for changed baselines and taste, not every routine test run.

**L4 — bounded session review, advisory.** Reuse Impeccable's Operate guidance and existing critique storage, adding structured findings beside it rather than another score service. A pointwise audit runs once when a UI milestone is selected. An on-demand PR comparison uses two ordered pairwise passes total (head/main, main/head), retaining agreed verdicts; disagreement remains uncertainty and is not a pass. Do not run every review command's full scoring workflow as an automatic loop. No paid service, model keys in CI, arbitrary scores or rewrite-until-pass behavior.

Inputs: 375/1440 light/dark captures where available, ARIA/text, incumbent tokens/brand decisions (future DESIGN.md documents them), PRODUCT.md vocabulary/persona/job, L1–L3 outcomes and prior owner decisions. Report only judgment beyond deterministic checks: hierarchy, redundant content, proportion, coherence and affordances. Missing required inputs mean `not_run`/unverified, not invented visual judgment.

Proposed finding fields: `fingerprint`, `scenario_id`, `source_sha`, `url`, `viewport`, `theme`, `motion`, `rubric_item`, `verdict` (`pass|fail|n.a.`), `evidence_status`, `severity`, `evidence`, `owner_tier` (`token|primitive|pattern|section|page|copy`), `model_id`, `prompt_version`. Scope and deduplicate by underlying cause while retaining affected cases. Pin the actual available model identifier and prompt revision; record the limitation if the service exposes only an alias.

Calibration uses owner-labelled examples only. Historical agent-directed fixes and critique scores are candidates for review, not owner ground truth. Report precision with TP/FP denominators and false-positive rate only when labelled negative examples exist; otherwise mark uncalibrated. Demote unreliable rubric items to optional judgment. Pairwise agreement alone does not establish correctness.

**L5 — bounded owner judgment and decisions.** Present only unresolved taste/strategy findings and key captures. Log fingerprint, scope, verdict, rationale, evidence/rubric version and actor. Suppress only the same rejected claim within that scope; changed evidence reopens review. Do not let aesthetic rejection suppress a security/accessibility regression. A repeated decision becomes a candidate machine rule or labelled example only when its semantics are safe to generalize.

**Ratchet:** use one small ledger for confirmed legacy violations with rule/scenario/semantic locator/theme/tier/owner/rationale/source evidence and disposition. Counts/entries may shrink, not silently grow. Tool-version or coverage changes need explicit re-baselining with provenance; finding an old defect for the first time is not evidence it is a new regression. Keep uncertain findings distinct. Start with new confirmed violations; do not freeze every heuristic as a release blocker.
