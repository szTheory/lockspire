# v1.29 Admin UI Journey & Design-System Research Summary

## Inputs

- Local admin route, LiveView, CSS, component, docs, and screenshot inventory inspection.
- Sidecar subagent research for information architecture/JTBD, design-system/CSS architecture, and accessibility/mobile risks.
- External design references requested by the user:
  - GOV.UK design principles: start with user needs, do less, make complex services simple, build services rather than isolated pages, and be consistent without forcing uniformity.
  - GOV.UK user-need and experience-map guidance: content and navigation should exist to satisfy a provable user task, and journeys should be mapped from the user's perspective.
  - Emil Kowalski animation guidance: motion should be natural, interruptible, performant, purposeful, short, and removable under reduced-motion preferences.

## Operator Model

The current admin route surface is real and broad enough to justify a second polish milestone. The stable top-level model remains:

- **Orient:** Overview.
- **Configure:** Clients, Security, Keys, DCR.
- **Support:** Consents, Tokens.
- **Operate:** Device Authorizations, Interactions, Logout Deliveries.

Primary personas:

- **Provider operator:** needs a cockpit for provider health, posture, and next actions.
- **Security/platform owner:** needs issuer policy, keys, client overrides, and safe lifecycle changes.
- **Partner-onboarding operator:** needs DCR policy, IATs, self-registered clients, and RAT handoff.
- **Support engineer:** needs account/client/token/consent investigation and safe revocation.
- **Runtime operator:** needs pending, retrying, failed, and completed protocol work to be scannable.

## Key Findings

- The v1.28 baseline is strong, but the next value is a route-by-route journey contract rather than another broad visual sweep.
- Overview must stay an attention cockpit, not a sitemap. It should prioritize abnormal posture and live incidents.
- IATs are part of DCR but are not top-level nav items, so DCR pages must make IAT inventory and minting obvious.
- DCR onboarding and DCR policy are separate jobs and need strong page titles/cross-links.
- Post-logout redirect URIs and logout propagation endpoints are easy to confuse and need precise labels everywhere.
- Support and operations are separate journeys, but real incidents often require pivots by client, account/subject, token family, session, consent, or delivery ID.
- Client detail is the densest page and the highest mobile-risk surface because identity, posture, logout, credentials, DCR/RAT, and actions compete for attention.
- Existing CSS has a good scoped BEM/design-token base, but raw colors, implicit layout constants, legacy list classes, and repeated raw LiveView structures can cause drift.
- Mobile nav, secondary nav, true tables, long IDs, long URLs, secrets, and action-bar stacking are the main screenshot regression risks.
- Accessibility is decent at the shell level, but error/confirmation semantics, disabled link behavior, focus proof, and color-independent status cues should be considered during implementation.

## Implementation Implications

- Phase 107 should produce the journey contract and audit before UI edits.
- Phase 108 should strengthen shared components and tokens, especially hero, summary grid, filter form, resource row, detail section, secret reveal, secondary nav, and action groups.
- Phase 109 should prioritize support and operations surfaces first, then DCR/IAT, keys, and client action grouping.
- Phase 110 should require desktop/mobile screenshots, mobile no-page-overflow checks, docs updates, and contract tests.

## Acceptance Notes

- No Tailwind migration, theming engine, hosted admin service, developer portal, or protocol-surface expansion.
- Keep `lockspire-admin-*` BEM/design-token CSS.
- Keep host-owned staff auth, MFA, role checks, tenant policy, layouts, and branding outside Lockspire.
- Use motion only for orientation, state continuity, and feedback; it must respect `prefers-reduced-motion`.
