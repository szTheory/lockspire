# v1.34 PostgreSQL Schema Decision

**Date:** 2026-06-30  
**Decision:** New generated installs should default to a dedicated `lockspire` PostgreSQL schema. Existing installs stay legacy-compatible unless they opt in.

## Why

Lockspire creates enough tables that using the host app's default public schema reads as namespace pollution. A dedicated schema is more respectful of Phoenix context boundaries and makes inspection, backup, cleanup, and ownership clearer.

## Tradeoffs

- Pro: cleaner host database namespace.
- Pro: easier operator/SRE inspection of Lockspire-owned state.
- Pro: better alignment with embedded-library "respectful guest" behavior.
- Con: every query and migration path must be prefix-aware.
- Con: existing users need an explicit migration plan before moving data.
- Con: Oban prefixing has to stay aligned with Lockspire prefix defaults.

## Footguns Avoided

- No silent public-to-lockspire data move.
- No reliance on `search_path` as hidden global state.
- No per-request tenant prefix support in v1; host tenant policy remains a host seam.
- No unqualified raw SQL in shipped migrations.

## Implemented Fix

- Prefix normalization rejects unsafe identifiers.
- Migrations use `Lockspire.Storage.Ecto.Migration`.
- Runtime repo calls pass prefix options.
- Oban migrations/runtime use `oban_prefix`, defaulting to `storage_prefix`.
- Install generator defaults to `lockspire`, and explicit `public` remains available.

## Future Work

Write an explicit data-move guide for existing public-schema installs if adopter demand appears.
